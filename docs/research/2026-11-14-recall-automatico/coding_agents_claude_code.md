## 1. Claude Code hook capabilities for automatic recall (events, output format, timeouts, async, size limits, transcript, caching)

### Takeaway
In Claude Code 2.1.3xx, a hook can inject text into the model through `hookSpecificOutput.additionalContext`. This works on SessionStart, SubagentStart, UserPromptSubmit, UserPromptExpansion, PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch, Stop, SubagentStop and PostModelSwitch. Plain stdout also counts as injected context on UserPromptSubmit, UserPromptExpansion, SessionStart and PostModelSwitch. Each injected string is capped at 10,000 characters. Claude Code wraps the text in a `<system-reminder>`, appends it to the conversation layer where the hook fired, and saves it in the transcript. Appending keeps the cached prompt prefix intact, but the injected text stays in history and is paid for on every later request. An `async: true` command hook can still reach the model: its `additionalContext` and `systemMessage` are delivered "on the next conversation turn". If the session is idle, nothing is delivered until the user's next interaction. The exception is `asyncRewake` with exit code 2, which wakes Claude immediately.

### Cited Findings
**Events that inject context, and where the text lands**
- [doc] Claude Code wraps `additionalContext` "in a system reminder and inserts it into the conversation at the point where the hook fired. Claude reads the reminder on the next model request, but it doesn't appear as a chat message in the interface." — [Hooks reference: Add context for Claude](https://code.claude.com/docs/en/hooks#add-context-for-claude)
- [doc] Where the reminder appears, by event: "SessionStart and SubagentStart: at the start of the conversation, before the first prompt"; "UserPromptSubmit and UserPromptExpansion: alongside the submitted prompt"; "PreToolUse, PostToolUse, PostToolUseFailure, and PostToolBatch: next to the tool result"; "Stop and SubagentStop: at the end of the turn. The conversation continues so Claude can act on the feedback"; "PostModelSwitch: with the next request after the switch." — [Hooks reference](https://code.claude.com/docs/en/hooks#add-context-for-claude)
- [doc] Plain stdout with exit 0: "`UserPromptSubmit`, `UserPromptExpansion`, `SessionStart`, and `PostModelSwitch`: Claude Code adds plain-text stdout as context that Claude can see and act on." On UserPromptSubmit, "Plain stdout and the `additionalContext` value are each injected as a system reminder that starts with the hook's name; Claude reads both," and "Neither channel produces a visible transcript entry." — [Hooks reference](https://code.claude.com/docs/en/hooks#userpromptsubmit)
- [doc] Events with no context or decision channel ("Used for side effects like logging or cleanup"): Setup, Notification, SessionEnd, PostCompact, InstructionsLoaded, StopFailure, CwdChanged, DirectoryAdded, FileChanged. PreCompact stdout "becomes instructions for the compaction summary." — [Hooks reference: Decision control table](https://code.claude.com/docs/en/hooks#decision-control)
- [doc] UserPromptSubmit "can't replace the prompt; it only injects `additionalContext` alongside it". Its input includes `prompt`, plus `session_title` when the session has a custom title. Its outputs are `decision: "block"`, `reason`, `additionalContext`, `sessionTitle` and `suppressOriginalPrompt`. — [Hooks reference](https://code.claude.com/docs/en/hooks#userpromptsubmit)
- [changelog] UserPromptSubmit hooks now run *before* a skill or custom slash command expands, so a blocking hook also stops the command's embedded shell commands. The version could not be isolated from the page. — [Changelog](https://code.claude.com/docs/en/changelog)
- [doc] PostToolBatch "runs once after every tool call in a batch has resolved, before Claude Code sends the next request to the model", whereas "`PostToolUse` fires once per tool, which means it fires concurrently when Claude makes parallel tool calls". PostToolBatch `additionalContext` is "injected once before the next model call." — [Hooks reference](https://code.claude.com/docs/en/hooks)
- [changelog] History of the injection channels: UserPromptSubmit `additionalContext` arrived in 1.0.59 (2025-07-23). The SessionStart hook arrived in 1.0.62 (2025-07-28). PreToolUse `additionalContext` arrived in 2.1.9 (2026-01-16). In 2.1.163 (2026-06-04), Stop and SubagentStop gained `hookSpecificOutput.additionalContext` "to give Claude feedback and keep the turn going without being labeled a hook error". — [Changelog](https://code.claude.com/docs/en/changelog)

**Output format**
- [doc] JSON output counts only when stdout holds "one JSON object... with nothing around it but whitespace". `hookSpecificOutput` "requires a `hookEventName` field set to the event name". The universal fields are `continue` (default true), `stopReason`, `suppressOutput` ("Has no effect"), `systemMessage` ("Warning message shown to the user") and `terminalSequence`. Canonical shape: `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"..."}}`. — [Hooks reference: JSON output](https://code.claude.com/docs/en/hooks#json-output)
- [doc] "When several hooks return `additionalContext` for the same event, Claude receives all of the values." "When an event fires, its matching hooks run in parallel," with at most 12 prompt or agent hooks running at once. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- [doc] If the string contains `<system-reminder>` or `</system-reminder>`, Claude Code replaces the tag's `<` with `&lt;`. — [Hooks reference](https://code.claude.com/docs/en/hooks#add-context-for-claude)
- [doc] Phrasing guidance: "Write the text as factual statements rather than imperative system instructions... Text framed as out-of-band system commands can trigger Claude's prompt-injection defenses, which causes Claude to surface the text to you instead of treating it as context." For static instructions, "prefer CLAUDE.md." — [Hooks reference](https://code.claude.com/docs/en/hooks#add-context-for-claude)
- [doc] Hook types are `command`, `http`, `mcp_tool`, `prompt` and `agent` (agent hooks are experimental). For an `mcp_tool` hook, "The tool's text output is treated like command-hook stdout." However, SessionStart at launch (including `--continue` and `--resume`) and every Setup event "fire before the session's MCP servers are available", so their `mcp_tool` hooks are skipped. When SessionStart fires later, after `/clear` or a compaction, its `mcp_tool` hooks do run. — [Hooks reference: MCP tool hooks](https://code.claude.com/docs/en/hooks)
- [changelog] Configuring a prompt or agent hook for SessionStart, Setup or SubagentStart produces an error telling you to "use a command-type hook instead". — [Changelog](https://code.claude.com/docs/en/changelog)

**Size limits**
- [doc] "A hook's `additionalContext`, `systemMessage`, and `initialUserMessage` strings, and its plain stdout, are capped at 10,000 characters." Each JSON field is measured on its own; plain stdout is measured as a whole. "If a value exceeds 10,000 characters, Claude Code writes the text to a file in the session directory and passes Claude the file path with a preview of up to the first 2,000 characters instead. Claude can read the file, but Claude Code doesn't ask it to." No setting or environment variable raises the cap. — [Hooks reference](https://code.claude.com/docs/en/hooks#add-context-for-claude)
- [changelog] Behavior change in 2.1.89 (2026-04-01): "Changed hook output over 10,000 characters to be saved to disk with a file path + a 2,000-character preview instead of being injected directly into context". In 2.1.314 (2026-10-30), PreCompact output also became "cut at 10,000 characters". — [Changelog](https://code.claude.com/docs/en/changelog)

**Timeouts and blocking**
- [doc] Default timeouts: "600 for `command`, `http`, and `mcp_tool`; 30 for `prompt`; 60 for `agent`. Claude Code lowers the `command`, `http`, and `mcp_tool` default to 30 on UserPromptSubmit, PreModelSwitch, and PostModelSwitch, and to 10 on MessageDisplay. SessionEnd hooks share a 1.5-second budget," raised up to 60 s when a longer per-hook timeout is configured. — [Hooks reference: common fields](https://code.claude.com/docs/en/hooks#common-fields)
- [doc] When a synchronous hook times out, Claude Code cancels it and discards its output, including any `additionalContext`. — [Hooks reference](https://code.claude.com/docs/en/hooks#userpromptsubmit)
- [doc] SessionStart: "When you start an interactive session, resume a conversation at launch with `--continue` or `--resume`, or run `/clear`, SessionStart hooks run in the background. You can type right away... Claude's first response still waits for the hooks to finish, so their context reaches Claude." The matchers and `source` values are `startup`, `resume`, `clear`, `compact` ("Auto or manual compaction") and `fork`. SessionStart outputs are `additionalContext`, `initialUserMessage` (`-p` mode), `sessionTitle`, `watchPaths` and `reloadSkills`; `CLAUDE_ENV_FILE` lets the hook persist environment variables. — [Hooks reference: SessionStart](https://code.claude.com/docs/en/hooks#sessionstart)
- [doc] SessionStart on resume receives cache-staleness fields: `context_tokens`, `prompt_cache_likely_expired` ("true when the last response is older than the session's prompt cache lifetime or a later compaction replaced the cached conversation") and `estimated_cache_write_usd`. — [Hooks reference](https://code.claude.com/docs/en/hooks#sessionstart)
- [doc] InstructionsLoaded fires with load reason `compact` "when instruction files are re-loaded after a compaction event" but has no decision or context control. — [Hooks reference](https://code.claude.com/docs/en/hooks)

**Async hooks: can their output reach the model later?**
- [doc] "Add `"async": true` to a command hook's configuration to run it in the background without blocking Claude. This field is only available on `type: "command"` hooks." Async hooks "can't block or control Claude's behavior: response fields like `decision`, `permissionDecision`, and `continue` have no effect." — [Hooks reference: Run hooks in the background](https://code.claude.com/docs/en/hooks#run-hooks-in-the-background)
- [doc] "After the background process exits, Claude Code delivers the `additionalContext` and `systemMessage` fields from the hook's JSON response to Claude on the next conversation turn, except for repeated SessionStart output. Unlike a synchronous hook's `systemMessage`, neither field is shown to you." — [Hooks reference: How async hooks execute](https://code.claude.com/docs/en/hooks#how-async-hooks-execute)
- [doc] "Hook output is delivered on the next conversation turn. If the session is idle, the response waits until the next user interaction. Exception: an `asyncRewake` hook that exits with code 2 wakes Claude immediately even when the session is idle." Separately, `asyncRewake` "runs in the background and wakes Claude on exit code 2. The hook's stderr, or stdout if stderr is empty, is shown to Claude as a system reminder." — [Hooks reference: Limitations](https://code.claude.com/docs/en/hooks#limitations)
- [doc] Claude Code does not enforce `timeout` on a running async hook, but it does enforce it on `asyncRewake`. "Each execution creates a separate background process." Under `-p`, Claude Code kills any async hook still running at teardown (outcome `cancelled`). — [Hooks reference](https://code.claude.com/docs/en/hooks#run-hooks-in-the-background)
- [doc] The async JSON response must be alone on stdout (multi-line output needs v2.1.295 or later) or sit on one line of its own. Fields of the wrong type are dropped. Async completion notices are hidden unless you use `--verbose` or Ctrl+O. — [Hooks reference](https://code.claude.com/docs/en/hooks#how-async-hooks-execute)
- [doc] Async SessionStart dedup: "Claude Code skips the hook's output when the `additionalContext` and `systemMessage` text matches what Claude last received from that hook... delivers the text when it changes, and again the next time the hook runs after a compaction or `/clear`. Before v2.1.295, Claude Code added the same text to the conversation again on every resume." — [Hooks reference: Limitations](https://code.claude.com/docs/en/hooks#limitations); [Changelog 2.1.295, 2026-10-08](https://code.claude.com/docs/en/changelog)
- [doc] An async PostToolUse hook cannot use `updatedToolOutput`, because its "response arrives after Claude Code records the tool result". — [Hooks reference](https://code.claude.com/docs/en/hooks)
- [changelog] Async hook completion messages have been suppressed by default since 2.1.75 (2026-03-13). — [Changelog](https://code.claude.com/docs/en/changelog)

**Transcript persistence and visibility**
- [doc] "Claude Code saves the injected text in the session transcript. For mid-session events like PostToolUse or UserPromptSubmit, when you resume with `--continue` or `--resume`, Claude Code replays the saved text rather than re-running the hook for past turns, so values like timestamps or commit SHAs become stale. SessionStart hooks run again on resume with `source` set to `"resume"`." — [Hooks reference](https://code.claude.com/docs/en/hooks#add-context-for-claude)
- [doc] SubagentStart re-runs: "Claude Code injects the returned context only when the subagent's context doesn't already hold the copy from an earlier run. The copy injected at launch stays in place, leaving the subagent's prompt cache intact." — [Hooks reference](https://code.claude.com/docs/en/hooks)

**Prompt caching**
- [doc] Each request is ordered in three layers. The System prompt layer holds core instructions and tool definitions. The Project context layer holds "CLAUDE.md, auto memory, unscoped rules" and changes when the "Session starts, or after `/clear` or `/compact`". The Conversation layer changes every turn. "An addition to the conversation layer leaves the system prompt and project context cached." — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- [doc] "Claude Code never invalidates the cache for a plugin's skills, commands, agents, hooks, monitors, or themes. It appends their content after the existing conversation." "Claude Code also appends system context mid-conversation, such as file-change notices, and marks that block for caching." — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- [doc] "Your project-root and user-level CLAUDE.md files are read once at session start and held in memory. Editing them mid-session does not invalidate the cache, but the edit also doesn't apply." — [Prompt caching](https://code.claude.com/docs/en/prompt-caching#editing-claude-md-mid-session)
- [changelog] A SessionStart cache regression was fixed in 2.1.277 (2026-09-18): "Fixed sessions continued after `/clear` (restart, `--continue`, `--resume`) missing part of their first message when a SessionStart hook printed output, causing a full prompt-cache miss". — [Changelog](https://code.claude.com/docs/en/changelog)

### Inferences
- Hooks offer four realistic automatic-recall triggers. (a) SessionStart (`startup|clear|compact`) can inject a session-level index or brief. (b) UserPromptSubmit can do synchronous per-prompt retrieval within a 30 s default budget; anything slower is discarded. (c) PreToolUse or PostToolUse can attach recall to what the agent is touching (file paths, grep terms). (d) An async hook (on UserPromptSubmit or PostToolUse) can deliver results one turn late. Option (d) suits slow retrieval that is not latency-critical, but it can never inform the turn that triggered it.
- Every injection is a permanent append to the conversation layer, so the cache prefix survives. Per-prompt recall therefore does not break caching, but each injected byte is re-sent (as a cache read) on every later turn until compaction. Under this model, cross-turn dedup and small budgets are what matter for cost. The docs never say this outright; I am combining the layer table with the append semantics.
- MCP tools are unavailable to `mcp_tool` hooks at launch SessionStart. A recall hook that must work on the first turn should therefore be a `command` (or `http`) hook that talks to the memory backend directly, not through the session's MCP client.
- Compaction discards earlier injections, and SessionStart re-fires with `source: "compact"`. That is the natural point to re-inject the index, which claude-mem, mem0 and basic-memory all do; see section 2.
- Because injected text is replayed verbatim on `--resume`, a recall hook should avoid volatile values (timestamps, "N minutes ago") in UserPromptSubmit and PostToolUse injections. SessionStart output, by contrast, is refreshed on resume.

### Gaps
- The docs do not say exactly where in the request the `<system-reminder>` for UserPromptSubmit sits relative to the user's text (same user message, before or after), or whether that block carries its own `cache_control` breakpoint. "System context mid-conversation... marks that block for caching" probably covers it, but this is not stated for hook reminders specifically.
- The docs give no total cap across multiple hooks for one event; only the per-string 10,000-character cap is documented.
- I found no documentation on whether async-hook output delivered "on the next conversation turn" is placed with the next user prompt or before the next model request inside an ongoing agentic loop (a tool-result turn). "Next conversation turn" is ambiguous, and verifying it would need an experiment.

## 2. How existing Claude Code memory plugins and MCPs actually do recall

### Takeaway
The leading plugins converge on a hybrid design. A **SessionStart** injection (index, profile or brief) is re-fired on `clear` and `compact` and is often skipped on `resume` to keep the cache. An optional **UserPromptSubmit** semantic search with tight gating (minimum prompt length, top-k 5–15, similarity threshold, hard timeout of 2–5 s, per-session dedup) adds to it. **Model-invoked search tools**, built for progressive disclosure (compact index, then full records), cover the rest. claude-mem keeps per-prompt injection **off by default** and adds file-scoped recall on PreToolUse(Read). claude-supermemory does per-prompt recall **by default**. The mem0 plugin searches **only on the first prompt** of a session. basic-memory uses only SessionStart plus PreCompact. Graphiti and other pure MCP servers rely on rules telling the model to "always search first".

### Cited Findings
**claude-mem (thedotmack/claude-mem, v15.18.3, 2026-11-12)**
- [code] Hook wiring: SessionStart has an async `claude-mem start` worker (startup|resume|clear|compact) and a **synchronous** `hook claude-code context` on `startup|clear|compact` only (timeout 60). UserPromptSubmit runs `session-init` (timeout 15). PreToolUse runs `file-context` on `Read|^read_file$|^Bash$|^Grep$|^Glob$|^memory_search$|^memory$|^mcp__.+__memory_search$` (timeout 15). PostToolUse and PostToolUseFailure run `observation` with `async: true`. Stop runs `summarize` async. - [doc/claim] "Continue and resume restore the existing conversation without printing or injecting a new timeline, preserving its prompt cache." - [code] The SessionStart budget is `CONTEXT_OUTPUT_LIMIT = 10_000` characters, matching Claude Code's cap. `fitContextToBudget` binary-searches down the session count and observation count until the rendered text fits. — [src/services/context/ContextBudget.ts](https://github.com/thedotmack/claude-mem/blob/main/src/services/context/ContextBudget.ts)
- [code] Defaults: `CLAUDE_MEM_CONTEXT_OBSERVATIONS: '50'`, `CLAUDE_MEM_CONTEXT_SESSION_COUNT: '10'`, `CLAUDE_MEM_CONTEXT_FULL_COUNT: '0'`. - [code] Gating: `SEMANTIC_CONTEXT_MIN_QUERY_CHARS = 20` and `SEMANTIC_CONTEXT_MAX_LIMIT = 20`. The code cites the project's own eval: "on a 19 KB file it cost -6% on Sonnet and +20% on Opus, on a 49 KB file -35% and -32%." — [src/cli/handlers/file-context.ts](https://github.com/thedotmack/claude-mem/blob/main/src/cli/handlers/file-context.ts)
- [code] Cross-turn dedup for file recall uses one gate per (session, file, observation-epoch), persisted in SQLite because "Each hook invocation is a freshly spawned process... an in-memory Set cannot remember what was already surfaced this session. ... A repeated Read of the same unchanged file is skipped unless a NEWER observation has landed since that injection." The claim is atomic (`INSERT ... RETURNING`), so concurrent Reads cannot both inject. — [src/cli/handlers/file-context-dedupe.ts](https://github.com/thedotmack/claude-mem/blob/main/src/cli/handlers/file-context-dedupe.ts)
- [code] "Piggyback" recall: when the agent reads Claude Code's native auto-memory dir (`~/.claude/projects/*/memory`), Codex memories, or calls a `memory_search` tool, a PreToolUse handler runs the same search with a query derived from the tool input (bounded to 500 chars and 1024 UTF-8 bytes, `MAX_CONTEXT_CHARS = 10_000`) and adds results as context. — [src/cli/handlers/memory-search.ts](https://github.com/thedotmack/claude-mem/blob/main/src/cli/handlers/memory-search.ts)
- [doc/claim] Model-invoked recall follows a 3-layer progressive disclosure: `search` returns a compact index (about 50–100 tokens per result), `timeline` gives context around an ID, and `get_observations(ids=[...])` fetches about 500–1,000 tokens per record. The doc itself says this "is a size ratio, not a measured recall or end-to-end saving" (issue #4138). — [docs/public/usage/search-tools.mdx](https://github.com/thedotmack/claude-mem/blob/main/docs/public/usage/search-tools.mdx)
- [doc] Compaction workaround on Codex: "`PostCompact` output cannot carry context, so the `PostCompact` hook marks the thread... and the thread's next `PostToolUse` returns the timeline as `additionalContext`, once." — [hooks-architecture.mdx](https://github.com/thedotmack/claude-mem/blob/main/docs/public/hooks-architecture.mdx)

There is no per-prompt hook; recall otherwise goes through MCP tools and skills. — [plugins/claude-code/hooks/hooks.json](https://github.com/basicmachines-co/basic-memory/blob/main/plugins/claude-code/hooks/hooks.json)

**Graphiti MCP (getzep/graphiti)**
- [doc] Recall is purely model-invoked and driven by rules: "Always search first: Use the `search_nodes` tool to look for relevant preferences and procedures before beginning work... Use the `search_facts` tool..." and "Capture requirements and preferences immediately... use `add_memory`." — [mcp_server/docs/cursor_rules.md](https://github.com/getzep/graphiti/blob/main/mcp_server/docs/cursor_rules.md)

### Inferences
- The products split on who decides to recall. Hook-driven recall (supermemory default; claude-mem opt-in; mem0 on the first prompt) gives deterministic coverage at a latency and token cost on every gated prompt. Model-driven recall (Graphiti, the claude-mem mem-search skill, supermemory advisory mode) costs nothing when memory is irrelevant but depends on the model choosing to search. supermemory's "discovery" note exists precisely because silence suppresses tool use.
- The 10,000-character hook cap appears as a design constant in claude-mem (`CONTEXT_OUTPUT_LIMIT = 10_000`, `MAX_CONTEXT_CHARS = 10_000`). Plugins size their injections to the host cap rather than to a relevance-driven budget.
- Per-prompt hooks use short timeouts (supermemory 4 s search inside a 5 s hook; mem0 2 s inside 6 s; claude-mem a single budget inside 15 s) and fail open. That is the practical latency envelope for synchronous recall on UserPromptSubmit.
- Persistent (DB or file) per-session dedup state is required because each hook runs as a fresh process. claude-mem uses SQLite rows; supermemory uses seen-hash state.

### Gaps
- I did not read claude-mem's SessionStart renderer (TimelineRenderer, HeaderRenderer) closely enough to quote the exact index row format or the token count of a typical injection.
- I did not inspect supermemory's per-session seen-hash storage location, or the exact scoring and reranking used by its API.
- No plugin publishes a measured evaluation of recall quality for per-prompt versus session-start injection. claude-mem explicitly notes that its token-saving figure is not a measured recall.
- I did not inspect OpenMemory MCP or other "memory-bank" MCP servers individually. Based on the Graphiti pattern, they are presumably model-invoked tools only, but this is unverified.

## 3. Native memory in coding tools: when it is loaded and how

### Takeaway
Native memory in coding tools is overwhelmingly **always-in-context at session start** (instruction files and a small index or summary), plus **on-demand reads** of detail. Claude Code loads `MEMORY.md` (first 200 lines or 25 KB) and reads topic files on demand. Codex injects a MEMORY_SUMMARY (8,900 bytes or less) and says rollout files are read only when they could change the answer. Gemini CLI concatenates GEMINI.md into every prompt plus just-in-time (JIT) subdirectory files. Cline Memory Bank reads all files at task start. Only Windsurf Cascade (memories "retrieve[d] when [Cascade] believes they are relevant") and Copilot Memory (citations validated before use) describe relevance-based retrieval, and neither documents the mechanism. Cursor removed its Memories feature in 2.1.x and relies on rules.

### Cited Findings
**Claude Code**
- [doc] "Claude Code has two complementary memory systems. Both are loaded at the start of every conversation." Auto memory is "Loaded into: Every session (first 200 lines or 25KB)". — [Memory docs](https://code.claude.com/docs/en/memory)
- [doc] "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded at the start of every conversation." "Claude Code doesn't load topic files such as `user_role.md`... at startup. Claude reads them on demand using its standard file tools." When MEMORY.md nears a limit, Claude Code reminds Claude to shorten it. Once over, the write succeeds but returns an error telling Claude to rewrite the index. — [Memory docs: auto memory](https://code.claude.com/docs/en/memory#auto-memory)
- [doc] The directory holds "a `MEMORY.md` index and one topic file per memory", at `~/.claude/projects/<project>/memory/`, shared across worktrees of a repo. It can be relocated with `autoMemoryDirectory` and disabled with `autoMemoryEnabled: false` or `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. — [Memory docs](https://code.claude.com/docs/en/memory#auto-memory)
- [doc] CLAUDE.md files above the working directory load at launch in full (files over 4 MiB are skipped). Subdirectory CLAUDE.md files and path-scoped rules "load on demand". "The main conversation's auto memory isn't loaded into subagents; the exception is a fork." — [Memory docs](https://code.claude.com/docs/en/memory)
- [doc] Project context (CLAUDE.md, auto memory) is read once per session and refreshed only on `/clear`, `/compact` or restart, which keeps the cached prefix stable. — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)

**OpenAI Codex (local memories)**
- [doc] "Local Codex memories are off by default." Once enabled, Codex turns useful context from eligible prior chats into local memory files in the background, "wait[ing] for a chat to be idle before summarizing". The store lives at `$CODEX_HOME/memories_v2/` (or the legacy `memories/`). The keys are `[features] memories = true`, `memories.generate_memories`, `memories.use_memories` ("whether Codex injects existing memories into future sessions"), `memories.disable_on_external_context`, `memories.extract_model` and `memories.consolidation_model`; `/memories` toggles per chat. — [ChatGPT/Codex docs: Memories](https://learn.chatgpt.com/docs/customization/memories?surface=app)
- [code] Injection mechanism: a developer-role `MemoryContextFragment::ReadInstructions` ("Memory-owned model context, capped below 10k tokens even for byte-heavy text") truncated to `TruncationPolicy::Bytes(8_900)`. — [codex-rs/core/src/context/memory.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/context/memory.rs)
- [code] Read-path template: "Use the injected MEMORY_SUMMARY as historical context... Read a matching rollout under `{{ base_path }}/rollout_summaries/` when its additional evidence, wording, chronology, or uncertainty could change your answer; otherwise do not retrieve history speculatively. Search selectively when a genuinely needed route is missing." Also "Memory is not proof of current behavior", "update memory only when the user explicitly asks" (by appending ad-hoc notes that consolidation applies), and a required `<oai-mem-citation>` block when a rollout summary informs the answer. The memory extension exposes list, read, search and ad_hoc_note tools. — [templates/memories/read_path_v2.md](https://github.com/openai/codex/blob/main/codex-rs/ext/memories/templates/memories/read_path_v2.md); [ext/memories/src/tools/](https://github.com/openai/codex/tree/main/codex-rs/ext/memories/src/tools)

**Gemini CLI**
- [doc] "It loads various context files from several locations, concatenates the contents of all found files, and sends them to the model with every prompt": global `~/.gemini/GEMINI.md`, then workspace and ancestor GEMINI.md files, then "Just-in-time (JIT) context files: When a tool accesses a file or directory, the CLI automatically scans for GEMINI.md files in that directory and its ancestors." — [docs/cli/gemini-md.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/gemini-md.md)
- [doc] The memory tool edits Markdown files (repo GEMINI.md, a private per-project folder, or global `~/.gemini/GEMINI.md`). "The stored facts are automatically included in the hierarchical context system for all future sessions." — [docs/tools/memory.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/tools/memory.md)
- [doc] Auto Memory (experimental, off by default) "mines your past Gemini CLI sessions in the background" for sessions "idle for at least three hours and contain at least 10 user messages". It writes candidate patches and skills to a review inbox and "never applies them without your approval." — [docs/cli/auto-memory.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/auto-memory.md)

**Windsurf (Cascade, now documented under Devin docs)**
- [doc] "During conversation, Cascade can automatically generate and store memories if it encounters context that it believes is useful to remember... Cascade's autogenerated memories are associated with the workspace that they were created in and Cascade will retrieve them when it believes that they are relevant. Memories generated in one workspace will not be available in another." "Creating and using auto-generated memories do NOT consume credits." — [Windsurf plugins docs: Memories & Rules](https://docs.devin.ai/windsurf/plugins/cascade/memories)
- [search-summary] The desktop docs locate memories in `~/.codeium/windsurf/memories/` and recommend Rules or AGENTS.md for durable knowledge. — [docs.windsurf.com memories.md (via search)](https://docs.windsurf.com/windsurf/cascade/memories.md)
- [doc] Change flag: `docs.windsurf.com/windsurf/cascade/memories` now 307-redirects to Devin docs. The Devin Local "customizations" page covers rules (`trigger`: `always_on`, `manual`, `model_decision`, `glob`; "injected into the agent's context at the start of every session"), skills, plugins, MCP and hooks, but does not mention Memories. — [Devin Local customizations](https://docs.devin.ai/desktop/cascade/memories)

**Cursor**
- [doc] Rules: "Always Apply", "Apply Intelligently" ("When Agent decides it's relevant based on description"), "Apply to Specific Files" (globs) and "Apply Manually" (@-mention). "When applied, rule contents are included at the start of the model context." AGENTS.md is supported at the root and in subdirectories. — [Cursor docs: Rules](https://cursor.com/docs/context/rules)
- [claim, conflicting] According to forum replies from Cursor staff, the Memories feature "was removed starting from version 2.1.17". Another staff reply says only the management UI was removed. Users can export memories to an `.mdc` file. — [Cursor forum: Custom modes and memories gone in 2.1](https://forum.cursor.com/t/custom-modes-and-memories-gone-in-2-1/143744); [Are my memories gone?](https://forum.cursor.com/t/are-my-memories-gone/144057)

**Cline**
- [doc] Memory Bank is "a documentation methodology", not a built-in retrieval system. Its six files are projectbrief, productContext, activeContext, systemPatterns, techContext and progress, and the custom instruction reads "I MUST read ALL memory bank files at the start of EVERY task - this is not optional". **GitHub Copilot Memory**
- [doc] "Copilot creates memories itself, as a byproduct of working with you." There are two kinds: repository-level facts (shared, used "only in operations on the same repository") and user-level preferences. Before use, "Copilot is instructed to check the citations provided with each memory" and upvotes or downvotes it. The default expiry is 90 days, reset on upvote; organizations can set 7–180 days. Surfaces: Copilot app, CLI, code review, cloud agent, Agentic Autofix, Mobile, Slack and Teams; in VS Code it is off until a local setting is enabled. — [GitHub Docs: Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)

### Inferences
- First-party tools favor a bounded always-loaded artifact plus agent-initiated detail reads: Claude Code's MEMORY.md and topic files; Codex's summary, rollout summaries and search tools. This maximizes prefix-cache stability because the artifact is frozen per session. None of the first-party coding tools documents per-prompt semantic injection.
- Codex and Copilot both build in staleness defenses ("Memory is not proof of current behavior"; citation validation). An injected recall should carry provenance (source, date) so the agent can verify it.
- Background consolidation of idle sessions, rather than capture at session end, is now common: Codex waits for idle chats, Gemini Auto Memory requires 3 h idle and 10 or more messages, and claude-mem runs async workers.

### Gaps
- Windsurf does not document how its "retrieve when relevant" works (embedding search versus model tool call versus always-in-prompt list).
- Copilot does not say whether memories are injected wholesale or retrieved per task.
- Codex does not document how the summary size is chosen beyond the 8,900-byte truncation, and it is unclear whether the injected fragment is re-sent after compaction.
- I could not confirm Cursor's removal in its official 2.1 changelog; the evidence comes from staff forum posts that conflict.

## 4. ChatGPT memory and OpenAI Agents SDK sessions

### Takeaway
ChatGPT has two mechanisms: saved memories (explicit) and reference chat history (an implicit, continually updated synthesis). OpenAI does not publicly document when retrieval happens or how the text is injected, and the help center blocked automated fetching. The OpenAI Agents SDK has no long-term memory retrieval: Sessions simply load and prepend stored history before every run, optionally limited to the last N items, filtered by a callback, or compacted.

### Cited Findings
- [search-summary] Saved memories are "details you have explicitly asked ChatGPT to remember". "Reference chat history" lets ChatGPT "use information from your past chats". Turning off saved memories also turns off chat history. Temporary Chats neither use nor create memories. Newer "improved memory" is "based on a continually updated synthesis of context from your past chats", and users can see which sources (memories, past chats, files) personalized a response. Memory management and automatic memory management are Plus and Pro on web. — [OpenAI Help: Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq); [How does memory use past conversations](https://help.openai.com/en/articles/10303002-how-does-memory-use-pastconversations) (both returned HTTP 403 to direct fetch; content comes from search-engine summaries)
- [doc] Agents SDK Sessions: the runner "automatically retrieves the conversation history for the session" and prepends it (history first, then the new input). New items are "automatically stored in the session" after the run. `SessionSettings(limit=N)` retrieves only the latest N items (the default is all). `session_input_callback(history, new_input)` must "Return the final list of input items that should be sent to the model". `OpenAIResponsesCompactionSession` compacts stored history after a turn when `should_trigger_compaction` is true. The page describes no separate long-term memory feature. — [OpenAI Agents SDK: Sessions](https://openai.github.io/openai-agents-python/sessions/)

### Inferences
- `session_input_callback` is the SDK's documented hook point for per-run retrieval (fetch memories and splice them into the input). As in Claude Code's UserPromptSubmit, recall in the SDK is the integrator's job, done synchronously before each model call.

### Gaps
- There is no official OpenAI statement on whether saved memories sit in the system prompt every turn, or whether chat-history references are retrieved per message versus summarized once per conversation. Third-party reverse-engineering exists, but I did not verify it and so do not cite it.
- I did not check for a newer Agents SDK "memory" module beyond Sessions.

## 5. Common patterns observed (synthesis)

### Takeaway
Three patterns dominate. (1) An **always-on small index or summary, frozen per session, with on-demand fetch**: Claude Code MEMORY.md, the Codex MEMORY_SUMMARY, the claude-mem SessionStart index, the supermemory profile, the basic-memory brief. (2) **Per-prompt retrieval with heavy gating and dedup**: supermemory by default, claude-mem opt-in, mem0 on the first prompt only. (3) **Contextual triggers tied to what the agent touches**: claude-mem PreToolUse(Read) file timelines, Gemini JIT GEMINI.md, Claude Code nested CLAUDE.md and path rules. Re-injection after compaction (SessionStart `compact`) and skipping on resume (cache preservation) are the norm among Claude Code plugins.

### Cited Findings
- Frozen per-session index: Claude Code loads MEMORY.md at conversation start and refreshes only on /clear, /compact or restart — [Memory](https://code.claude.com/docs/en/memory), [Prompt caching](https://code.claude.com/docs/en/prompt-caching). Codex injects the summary as a developer fragment of 8,900 bytes or less — [memory.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/context/memory.rs). claude-mem injects on `startup|clear|compact` but not `resume`, "preserving its prompt cache" — [hooks.json](https://github.com/thedotmack/claude-mem/blob/main/plugin/hooks/hooks.json), [hooks-architecture.mdx](https://github.com/thedotmack/claude-mem/blob/main/docs/public/hooks-architecture.mdx).
- Index first, then fetch: claude-mem search, then timeline, then get_observations — [search-tools.mdx](https://github.com/thedotmack/claude-mem/blob/main/docs/public/usage/search-tools.mdx). Codex: summary first, then rollout_summaries "only when it could change your answer" — [read_path_v2.md](https://github.com/openai/codex/blob/main/codex-rs/ext/memories/templates/memories/read_path_v2.md). Claude Code: MEMORY.md index, then topic files read on demand — [Memory](https://code.claude.com/docs/en/memory).
- Per-prompt gating parameters seen in practice: minimum prompt length of 12 chars (supermemory) or 20 chars (claude-mem, mem0); top-k of 5 (claude-mem, mem0) or up to 15 (supermemory); similarity 0.55 or higher (supermemory); 300 chars per result (supermemory); search timeouts of 2–4 s inside 5–15 s hook timeouts — [recall-directive.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/recall-directive.js), [semantic-context.ts](https://github.com/thedotmack/claude-mem/blob/main/src/shared/semantic-context.ts), [hook_runner.py](https://github.com/mem0ai/mem0/blob/main/integrations/claude-code-plugin/core/hook_runner.py).
- Dedup across turns: supermemory's seen hashes ("already in context") — [recall-directive.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/recall-directive.js); claude-mem's (session, file, epoch) SQLite gate — [file-context-dedupe.ts](https://github.com/thedotmack/claude-mem/blob/main/src/cli/handlers/file-context-dedupe.ts); Claude Code's own async-SessionStart identical-text suppression (v2.1.295) — [Hooks: Limitations](https://code.claude.com/docs/en/hooks#limitations).
- Async capture and sync recall: every plugin examined runs capture (PostToolUse, Stop, SessionEnd) async or with tiny timeouts, and recall synchronously — [claude-mem hooks.json](https://github.com/thedotmack/claude-mem/blob/main/plugin/hooks/hooks.json), [supermemory hooks.json](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/hooks.json), [mem0 hooks.json](https://github.com/mem0ai/mem0/blob/main/integrations/claude-code-plugin/hooks/hooks.json).
- Staleness and provenance: Copilot checks citations before use — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory); Codex says "Memory is not proof of current behavior" and requires citations — [read_path_v2.md](https://github.com/openai/codex/blob/main/codex-rs/ext/memories/templates/memories/read_path_v2.md).
- Misses: supermemory injects a one-time discovery note on an empty result instead of staying silent — [recall-directive.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/recall-directive.js).

### Inferences
These are design implications for automatic recall in Claude Code. They are my analysis, not documented facts.
- **A baseline that fits the host's cache model**: a synchronous `command` SessionStart hook on `startup|clear|compact` that injects a compact, provenance-tagged index or brief well under 10,000 chars, and does not re-inject on `resume` (or relies on the 2.1.295 dedup for async SessionStart).
- **Per-prompt recall as a gated add-on**: UserPromptSubmit with a hard internal budget (about 2–4 s, against the 30 s host default, failing open), a minimum prompt length, top-k 3–5, a similarity floor, and persistent per-session dedup keyed by memory ID, so the same item never enters history twice. Every injection is permanent in the conversation layer until compaction.
- **Slow or deep retrieval**: an `async: true` hook can deliver results on the next turn. Combined with the PostToolUse or PostToolBatch timing, results can land mid-loop "next to the tool result". `asyncRewake` exists only for exit-2 alerts, not routine recall.
- **Contextual triggers**: PreToolUse or PostToolUse on Read, Grep and Edit paths (as claude-mem does) give targeted, low-noise recall tied to files. Dedup by (session, path, newest-memory-epoch) prevents repetition.
- **Phrasing**: injected text should be factual ("Prior decision (2026-10-02, source X): …"), not imperative, to avoid Claude's prompt-injection defenses. The docs explicitly warn about this.
- **Pairing with model-invoked tools**: hooks should complement a model-invoked recall tool, with a discovery hint on misses, because the model will not call a tool that nothing mentions.

### Gaps
- None of the sources offers a controlled comparison of session-start-only versus per-prompt injection versus model-invoked recall on coding-task outcomes. Choosing among them remains a design judgment, best settled with a local eval.
- I could not verify empirically whether async-hook results delivered during an agentic loop (between tool calls) count as the "next conversation turn". The docs' wording and example (tests reporting back after a Write) suggest yes, but an experiment is needed.
