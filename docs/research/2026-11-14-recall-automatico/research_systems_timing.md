# When an LLM agent should retrieve from memory: research systems (Hindsight, EverMemOS, A-MEM, ReasoningBank) and the retrieval-timing literature

Notes compiled 2026-11-14. Verification legend: **[V]** means the claim was read from the primary source during this session (arXiv HTML or official docs). **[K]** means the claim comes from a well-known primary paper cited by its arXiv ID but was not re-fetched this session, so a report writer should treat exact figures as "to confirm". **[S]** means it came only from a search-engine summary or snippet (secondary). All benchmark numbers are author-reported unless stated otherwise. Different benchmarks are never merged into one ranking.

## 1. Hindsight (Vectorize.io): when recall runs, what it returns, latency, and how reflect differs

### Takeaway
The Hindsight paper defines recall as a query plus token-budget call that returns a ranked, budget-packed list of facts. It does not say when an agent should call it. The official integrations do answer that: the default is **automatic recall before every turn**, injected into the system prompt, and model-callable `recall`/`reflect` tools are offered as an alternative or an addition (Hermes "hybrid" mode does both). The paper reports no latency numbers.

### Cited Findings
- Paper: "Hindsight is 20/20: Building Agent Memory that Retains, Recalls, and Reflects", by Latimer, Boschi, C. Bartholomew (Vectorize.io), Neeser (Washington Post), Srivastava, Wang, Ramakrishnan (Virginia Tech). arXiv 2512.12818v1, 14 Dec 2025. [V] — [arXiv 2512.12818](https://arxiv.org/html/2512.12818)
- **Retain** turns conversation into narrative facts with temporal ranges, resolves entities, sorts each fact into one of four networks (world, experience, opinion, observation), builds graph links, and reinforces opinions when new evidence arrives. [V] — [arXiv 2512.12818](https://arxiv.org/html/2512.12818)
- **Recall** takes (bank, query, token budget) and returns as many facts as fit the budget. Four retrieval channels run in parallel: (1) semantic cosine search over an HNSW pgvector index; (2) BM25 over a GIN index; (3) graph spreading activation that starts from the top semantic hits and follows entity, causal, temporal and semantic links; (4) temporal retrieval, which only runs when a time constraint is detected (a rule-based parser, with flan-t5-small as fallback). The channels are fused with Reciprocal Rank Fusion (k=60), rescored by a cross-encoder (ms-marco-MiniLM-L-6-v2), and packed greedily in relevance order until the token budget runs out. An optional cost/latency budget can cap how far the search expands. [V] — [arXiv 2512.12818](https://arxiv.org/html/2512.12818)
- **Reflect** first calls recall, then generates an answer conditioned on a behavioral "disposition" profile (skepticism, literalism, empathy, bias strength). It may also form or update opinions with confidence scores. Recall only retrieves; reflect retrieves, reasons, and writes back (opinions). [V] — [arXiv 2512.12818](https://arxiv.org/html/2512.12818)
- The paper does not specify when recall is invoked (per turn, as a tool, or before the response), reports no latency measurements, and does not discuss whether to retrieve at all. The only conditional behavior is the temporal channel and the optional cost cap. [V] (the last ~21k characters of the HTML were not read) — [arXiv 2512.12818](https://arxiv.org/html/2512.12818)
- Benchmarks (author-reported, judge GPT-OSS-120B). LongMemEval-S (500 Q): 83.6% with OSS-20B, 89.0% with OSS-120B, 91.4% with Gemini-3 Pro as the answer generator, against full-context baselines of 60.2% (GPT-4o) and 39.0% (OSS-20B). LoCoMo: 83.18% (OSS-20B), 85.67% (OSS-120B), 89.61% (Gemini-3). Zep and Supermemory baselines were copied from the Supermemory technical report, not rerun. A Backboard figure of 90.00% is self-reported by Backboard. The fetch flagged an internal inconsistency: the introduction gives 85.67% for the 20B LoCoMo run, while the table gives 83.18%. [V] — [arXiv 2512.12818](https://arxiv.org/html/2512.12818)
- **Claude Agent SDK integration (guide dated 17 Jul 2026):** `create_memory_hooks` makes the agent "recall relevant memories before each prompt and retain results after each session" with no tool calls. `create_hindsight_server` instead exposes retain/recall/reflect as MCP tools "the agent calls when it judges memory relevant". The docs' guidance: use tools if the agent should decide when memory matters, and hooks if recall/retain should happen every turn. Both paths can share a `bank_id`. Hook config fields: `auto_recall`, `auto_retain`, `retain_on_tools` (e.g. `["Bash"]`), `recall_max_results` (5 in the example), `retain_tags`. `configure` takes `budget="mid"`, but the levels are not documented on that page. [V] — [Hindsight guide: Claude Agent SDK](https://hindsight.vectorize.io/guides/2026/07/17/guide-claude-agent-sdk-memory-with-hindsight)
- Other integrations default to per-turn auto-recall. Haystack's `HindsightMemoryWrapper` injects memories into the system prompt before each turn when `auto_recall` is on. OpenAI Agents SDK `memory_instructions()` injects on every turn. The Microsoft Agent Framework context provider recalls on every run, with independent `auto_recall`/`auto_retain` toggles. Hermes Agent's default `hybrid` mode auto-injects before every turn **and** exposes recall/retain/reflect tools, with `retain_every_n_turns` defaulting to 1. The OMO plugin's `retainEveryNTurns` defaults to 10. "Right agent" auto-recalls on every new user message, with an optional `recall_budget` token cap. [S] — [Haystack blog](https://hindsight.vectorize.io/blog/2026/06/11/haystack-persistent-memory); [OpenAI Agents guide](https://hindsight.vectorize.io/guides/2026/07/17/guide-openai-agents-memory-with-hindsight); [Agent Framework blog](https://hindsight.vectorize.io/blog/2026/06/18/microsoft-agent-framework-memory); [Hermes provider blog](https://hindsight.vectorize.io/blog/2026/04/06/hermes-native-memory-provider); [Hermes README](https://gitcode.com/ChrisBob/hermes-agent/blob/main/plugins/memory/hindsight/README.md); [OMO guide](https://hindsight.vectorize.io/guides/2026/07/17/guide-omo-memory-with-hindsight); [Right agent](https://hindsight.vectorize.io/sdks/integrations/right-agent)
- In its "Agent Memory Benchmark" manifesto (23 Mar 2026), Vectorize reportedly says an "agentic" mode, where the LLM issues its own memory queries, does consistently better on complex and multi-hop questions, at the cost of more latency and tokens from extra round-trips. [S] (search summary only, not opened) — [Hindsight blog: Agent Memory Benchmark](https://hindsight.vectorize.io/blog/2026/03/23/agent-memory-benchmark)

### Inferences
- Hindsight's production answer to "when" is **per-turn automatic recall with a result cap (`recall_max_results`) or a token budget, plus optional tools for deeper, model-driven queries**. The research paper pushes relevance control into the ranking stack (RRF, cross-encoder, token packing) rather than into a "should I retrieve" gate.
- Reflect is a heavier operation (recall plus an LLM generation plus opinion writes). For a coding agent it fits as an explicit tool, not as a per-turn hook.

### Gaps
- No latency figures (p50/p95) for recall in the paper or in the guides I read. The budget levels ("low/mid/high") are not defined in the sources I read.
- None of the Hindsight docs I read say whether per-turn injection deduplicates memories already injected on earlier turns.
- The tail of the arXiv HTML (~21k chars, likely appendices) was not read, and the benchmark manifesto was not opened.

## 2. EverMemOS (EverMind): how retrieval is triggered, what is injected, cost, benchmark claims

### Takeaway
EverMemOS retrieves **once per query**, using hybrid dense+BM25 scoring over atomic facts that selects MemScenes. It then reranks episodes and runs an **LLM sufficiency check that triggers query rewriting and a second retrieval round on about 31% of LoCoMo questions**. This is a retrieve-always pipeline with an adaptive "retrieve more" loop, not a "whether to retrieve" gate. Its benchmark leads are author-reported, and its LongMemEval baselines were copied from a leaderboard rather than rerun.

### Cited Findings
- Paper: "EverMemOS: A Self-Organizing Memory Operating System for Structured Long-Horizon Reasoning", by Chuanrui Hu, Xingze Gao, … Lidong Bing, Yafeng Deng (EverMind / Shanda Group). arXiv 2601.02163, v1 5 Jan 2026, v2 9 Jan 2026. [V] — [arXiv 2601.02163](https://arxiv.org/html/2601.02163); dates per [search result](https://arxiv.org/abs/2601.02163v1)
- The system has three phases. (I) Episodic Trace Formation turns dialogue into **MemCells**: an episode (a short third-person narrative), atomic facts, **Foresight** (forward-looking inferences with validity intervals), and metadata (timestamps, source pointers). (II) Semantic Consolidation clusters MemCells into thematic **MemScenes** by embedding similarity to scene centroids, using a threshold (join the nearest scene or create a new one), and updates **user profiles**. (III) Reconstructive Recollection does retrieval. [V]/[S] — [arXiv 2601.02163](https://arxiv.org/html/2601.02163); [search summary](https://www.emergentmind.com/topics/memscene)
- Retrieval pipeline. Retrieval is query-driven, and the paper gives no rule for running it every turn or behind a gate. Dense retrieval (Qwen3-Embedding-4B) and BM25 over atomic facts are fused with RRF. Each MemScene is scored by its best MemCell, and the top N=10 scenes are kept. Their episodes are pooled, reranked with Qwen3-Reranker-4B, and cut to K=10. Only Foresight items whose validity interval contains the current time are kept. An LLM verifier then returns a strict JSON sufficiency judgment. If the context is insufficient, it generates 2–3 rewritten queries (keyword, natural question, HyDE-style) and retrieves again. With GPT-4.1-mini, **31.0% of LoCoMo questions triggered the second round**. [V] — [arXiv 2601.02163](https://arxiv.org/html/2601.02163)
- What is injected depends on the mode. **Reasoning mode** (used for the benchmarks) injects retrieved episodes only. **Chat mode** injects episodes plus the user profile and time-valid Foresight. [V] — [arXiv 2601.02163](https://arxiv.org/html/2601.02163)
- Cost. On LoCoMo with GPT-4.1-mini, phase III (search plus answer) used about 10.27M tokens, roughly 6.7k per question. Memory construction (phase I) used 9.42M tokens. Table 1 lists "Avg. Tokens" of about 2.3k for EverMemOS, but the column is not defined. **No latency numbers are given**, and the Limitations section admits that LLM-mediated construction and retrieval add latency and cost, leaving caching, batching and async execution to future work. [V] — [arXiv 2601.02163](https://arxiv.org/html/2601.02163)
- Results (author-reported; judge is GPT-4o-mini plus two auxiliary judges; Cohen's κ against humans 0.891 on LoCoMo and 0.978 on LongMemEval, from only 25+25 pairs):
  - LoCoMo, GPT-4.1-mini: **93.05** vs Zep 85.22, MemOS 80.76, MemU 66.67, Mem0 64.20.
  - LoCoMo, GPT-4o-mini: **86.76** vs Zep 81.06.
  - LongMemEval-S, GPT-4.1-mini: **83.00** vs MemOS 77.80, Mem0 66.40, Zep 63.80.
  - LoCoMo baselines were rerun with official APIs. **LongMemEval baselines were copied from the MemOS leaderboard, not rerun.** [V] — [arXiv 2601.02163](https://arxiv.org/html/2601.02163)
- Ablations. Removing external memory, then MemScenes, then MemCells degrades performance step by step (figure only, no numbers in the text). Semantic segmentation scores 89.16–89.78, against 88.05 for fixed 10-message chunks and 84.52 for 1024-token chunks. On PersonaMem-v2, episodes plus profile score 53.25 vs 43.93 for episodes only. **There is no dedicated ablation of the sufficiency check / agentic re-retrieval.** [V] — [arXiv 2601.02163](https://arxiv.org/html/2601.02163)

### Inferences
- EverMemOS's adaptive element answers "is what I retrieved enough?", not "should I retrieve?". It pays an LLM verification call on every query, plus extra retrieval rounds on about a third of queries. That works for offline QA benchmarks but is expensive as a per-turn hook in a latency-sensitive coding loop.
- Splitting injection into "reasoning mode = episodes only" and "chat mode = episodes + profile + foresight" is a useful pattern: inject stable profile and preferences cheaply, and retrieve episodic detail per query.

### Gaps
- I did not inspect the EverMemOS GitHub repo, so the production per-turn pipeline, API latency, and any repo-claimed scores are not covered.
- Without an ablation of the sufficiency check, its contribution is unquantified. A search hit suggested an ACL 2026 version (aclanthology 2026.acl-long.2125), but I did not confirm that it is this paper.

## 3. A-MEM (Agentic Memory): retrieval at inference, link-following, evolution timing

### Takeaway
A-MEM puts its intelligence on the **write path**: notes, LLM-generated keywords and tags, link generation, and memory evolution all run when a memory is added. Read-time retrieval is plain top-k cosine similarity (default k=10). Accuracy rises with k and then plateaus or dips slightly, so even here more retrieved context stops helping.

### Cited Findings
- Paper: "A-Mem: Agentic Memory for LLM Agents", by Wujiang Xu, Zujie Liang, Kai Mei, Hang Gao, Juntao Tan, Yongfeng Zhang (Rutgers / AIOS Foundation). arXiv 2502.12110, first posted Feb 2025, v11 dated 8 Oct 2025. There are two repos (AgenticMemory for the benchmark, A-mem-sys for production). [V] — [arXiv 2502.12110](https://arxiv.org/html/2502.12110)
- Each note stores the content, a timestamp, LLM-generated keywords, tags, a context description, an embedding (all-MiniLM-L6-v2 over the concatenated fields), and links. **Link generation** runs at write time: the top-k nearest notes are found by cosine similarity, and an LLM decides which links to create. **Memory evolution** also runs at write time, right after linking: for each neighbor, the LLM decides whether to update its context, keywords and tags, and the evolved note replaces the old one. [V] — [arXiv 2502.12110](https://arxiv.org/html/2502.12110)
- **Retrieval at inference** (Sec. 3.4): the query is embedded with the same encoder, cosine similarity is computed against all notes, and the top-k are returned (default k=10) and added to the prompt as historical context. Figure 2 says linked memories are accessed during retrieval, **but Sec. 3.4 contains no link-traversal step**, so the paper is internally inconsistent on link-following. [V] — [arXiv 2502.12110](https://arxiv.org/html/2502.12110)
- **The k ablation** (GPT-4o-mini, k=10 to 50): performance rises, then plateaus or drops slightly at higher k, especially on Multi-Hop and Open-Domain. The chosen k is 40–50 for GPT models and 10 for most open models. [V] — [arXiv 2502.12110](https://arxiv.org/html/2502.12110)
- Cost. About 1,200 tokens per memory operation, versus about 16,900 for the LoCoMo and MemGPT baselines (85–93% fewer). Under $0.0003 per operation. Processing takes about 5.4 s per operation with GPT-4o-mini and 1.1 s with Llama 3.2 1B. Retrieval time goes from 0.31 µs at 1k notes to 3.70 µs at 1M notes. [V] — [arXiv 2502.12110](https://arxiv.org/html/2502.12110)
- LoCoMo F1, GPT-4o-mini: Multi-Hop 27.02 vs MemGPT 26.65; Temporal 45.85 vs MemGPT 25.52; Adversarial 50.03 vs the LoCoMo baseline's 69.23 (the baseline wins). The "≥2× multi-hop" claim is not supported for GPT-4o-mini in the table. Ablation (Multi-Hop F1): 9.65 without linking and evolution, 21.35 without evolution, 27.02 for the full system. Single runs, no error bars. [V] — [arXiv 2502.12110](https://arxiv.org/html/2502.12110)

### Inferences
- The ablation suggests the gains come from **enriching notes at write time** (keywords, context, links). For a coding agent, investing in write-time enrichment lets read-time recall stay cheap and run often.
- The 5.4 s per operation is write-path cost (LLM calls), not read latency. Read-time vector lookup is negligible.

### Gaps
- It is unclear whether the released code follows links at retrieval time. The repos were not inspected.
- A-MEM is evaluated in an offline QA setup (LoCoMo, DialSim), with no agent-loop experiment on when to retrieve.

## 4. ReasoningBank (Google): retrieval timing, top-k, injection, MaTTS, and results

### Takeaway
ReasoningBank retrieves **once, at task start, keyed on the task query**. It uses gemini-embedding-001 cosine similarity with **top-k=1 as the default**, and injects the item into the system prompt with an instruction to decide at each step whether to use it. Its retrieval-count ablation is among the clearest evidence that more retrieved memory hurts: k=1 scores 49.7, while k=2/3/4 score 46.0/45.5/44.4 (no memory: 39.0).

### Cited Findings
- Paper: "ReasoningBank: Scaling Agent Self-Evolving with Reasoning Memory", by Siru Ouyang, Jun Yan, I-Hung Hsu, … Jiawei Han, Chen-Yu Lee, Tomas Pfister (Google Cloud AI Research / UIUC). arXiv 2509.25140, first posted Sep 2025, v2 revised 16 Mar 2026. [V] — [arXiv 2509.25140](https://arxiv.org/html/2509.25140)
- **Timing:** "When facing a new task, the agent retrieves relevant memories". The agent "queries ReasoningBank with the current query context". The injected instruction says: "In each step, please first explicitly discuss if you want to use each memory item or not." So retrieval happens once per task and use is decided per step by the model. [V] — [arXiv 2509.25140](https://arxiv.org/html/2509.25140)
- **Method:** the task query is embedded with gemini-embedding-001 (Vertex AI), cosine similarity is computed over the pool, and the top-k are taken (**default k=1**). Items are concatenated into the **system prompt** as title + content. Each item has a title, a one-sentence description, and content (reasoning steps or insights), with at most 3 items extracted per trajectory. [V] — [arXiv 2509.25140](https://arxiv.org/html/2509.25140)
- **Extraction:** an LLM-as-judge (same backbone, temperature 0) labels each trajectory Success or Failure without ground truth. Successes yield strategies, and failures yield pitfalls or preventive lessons. Judge accuracy on Shopping is 72.7%. Simulated judge accuracy between 70% and 90% changed the success rate little. Consolidation is simple addition with no pruning or merging. [V] — [arXiv 2509.25140](https://arxiv.org/html/2509.25140)
- **Retrieval-count ablation** (App. C.1, WebArena-Shopping, Gemini-2.5-flash): success rate 39.0 (k=0), **49.7 (k=1)**, 46.0 (k=2), 45.5 (k=3), 44.4 (k=4). The authors' explanation: "excessive experiences may introduce conflicts or noise", and "the relevance and quality of memory are more crucial than sheer quantity." [V] — [arXiv 2509.25140](https://arxiv.org/html/2509.25140)
- **WebArena overall SR** (No Memory → ReasoningBank → +MaTTS): Gemini-2.5-flash 40.5 → 48.8 → 51.8; Gemini-2.5-pro 46.7 → 53.9 → 56.3; Claude-3.7-sonnet 41.7 → 46.3 → 48.8. Baselines Synapse and AWM fall in between or below. Steps per task also drop (flash: 9.7 → 8.3). [V] — [arXiv 2509.25140](https://arxiv.org/html/2509.25140)
- **SWE-Bench-Verified resolve rate:** flash 34.2 (no memory) / 35.4 (Synapse) / **38.8** (ReasoningBank); pro 54.0 / 53.4 / **57.4**. Average steps for pro fall from 21.1 to 19.8. No MaTTS result is reported on SWE-bench. Mind2Web task-level SR is very low in absolute terms (e.g. cross-task 3.3 → 4.8 for flash). [V] — [arXiv 2509.25140](https://arxiv.org/html/2509.25140)
- **MaTTS** (memory-aware test-time scaling). The parallel variant generates multiple trajectories per query and uses self-contrast to keep consistent patterns and filter spurious ones. The sequential variant uses iterative self-refinement, whose intermediate notes also feed extraction. On Shopping with k=5 trajectories: parallel Best-of-5 reaches 55.1 vs 49.7 at k=1, sequential reaches 54.5, and vanilla TTS without memory-aware extraction reaches 52.4 (parallel) and 51.9 (sequential). MaTTS changes **what gets written** to memory, not when retrieval happens. [V] — [arXiv 2509.25140](https://arxiv.org/html/2509.25140)
- Limitations: the authors "intentionally adopt simple embedding-based retrieval". Adaptive retrieval is described as compatible but out of scope. There is no ablation of retrieval timing (start-of-task vs per-step). [V] — [arXiv 2509.25140](https://arxiv.org/html/2509.25140)

### Inferences
- The best-supported pattern for coding agents in this set (it includes SWE-bench-Verified) is **one retrieval at task start, very small k (1 to a few), distilled strategy or pitfall items rather than raw transcripts, and the model explicitly told it may ignore items**.
- The k ablation is a single benchmark, a single backbone, and single runs. It is suggestive rather than definitive, but it agrees in direction with A-MEM's plateau and with the distractor literature in section 6.

### Gaps
- The exact memory-injection system prompt template was not in the fetched content. Per-step re-retrieval was not tested.

## 5. Adaptive-retrieval literature: always vs triggered vs model-decides, gating signals, and the cost of always retrieving

### Takeaway
Across RAG QA research, **adaptive retrieval matches or modestly beats always-retrieve while using far fewer retrieval calls**. Cheap gating signals (token-level uncertainty, query-complexity classifiers, entity popularity) are competitive with elaborate pipelines. Always-retrieve can **lower** accuracy when the model already knows the answer. For agent memory, the newest work (2026) moves toward learned or bandit controllers, but the evidence there is thinner and author-reported.

### Cited Findings
- **Large comparison (35 methods):** Moskvoretskii et al., "Adaptive Retrieval without Self-Knowledge? Bringing Uncertainty Back Home", arXiv 2501.12835 (v2 21 Feb 2025). It compared 8 adaptive-RAG systems (IRCoT, Adaptive-RAG, FLARE, DRAGIN, SeaKR, three Rowen variants) and 27 uncertainty-estimation (UE) gates (logit-based, consistency-based, internal-state, hybrid), using LLaMA-3.1-8B-Instruct, BM25 over Wikipedia, and 6 QA datasets (500 Q each). [V] — [arXiv 2501.12835](https://arxiv.org/html/2501.12835)
  - **Always-retrieve is not uniformly better than never-retrieve.** Never vs always (in-accuracy): NQ 0.446 vs 0.496; SQuAD 0.176 vs 0.312; HotpotQA 0.286 vs 0.410; but **TriviaQA 0.636 vs 0.610 and MuSiQue 0.106 vs 0.100, where retrieval hurt**. [V] — [arXiv 2501.12835](https://arxiv.org/html/2501.12835)
  - **Efficiency:** the best UE gates use about 0.28–0.99 retrieval calls (RC) and about 1.3–2.0 LM calls per question. IRCoT uses 2.7–4.4 RC, DRAGIN 2.1–3.2, FLARE 1.4–4.1, SeaKR 1.0–2.4, Adaptive-RAG 0.5–3.6. Rowen variants use 7–10 RC and 29–80 LM calls. [V] — [arXiv 2501.12835](https://arxiv.org/html/2501.12835)
  - **Accuracy:** simple UE gates beat the best complex baseline on single-hop NQ and SQuAD, roughly tie on TQA (0.662 vs 0.666), and **trail on multi-hop** (2Wiki 0.384 vs DRAGIN 0.456; HotpotQA 0.414 vs IRCoT 0.438; MuSiQue 0.104 vs Adaptive-RAG 0.140). The "best UE" figures are a per-dataset oracle pick, so they are optimistic. [V] — [arXiv 2501.12835](https://arxiv.org/html/2501.12835)
  - **Signal quality:** internal-state methods (SeaKR) are cheap but overconfident, with ROC-AUC 0.77–0.78 on single-hop that collapses to 0.37 on 2Wiki. The trained query-complexity classifier (Adaptive-RAG) reaches 0.71 on 2Wiki. Mean entropy and SAR lead on self-knowledge ROC-AUC (about 0.71–0.74). After domain transfer, gates tend to over-call the retriever. Oracle gating shows large remaining headroom. [V] — [arXiv 2501.12835](https://arxiv.org/html/2501.12835)
- **FLARE** (Jiang et al., arXiv 2305.06983, May 2023): active retrieval during long-form generation. It drafts the next sentence, and if any token's probability falls below a threshold, it retrieves using that draft (with low-confidence tokens masked, or turned into questions) as the query, then regenerates. The trigger is generation-time token uncertainty. [K] — [arXiv 2305.06983](https://arxiv.org/abs/2305.06983)
- **Self-RAG** (Asai et al., arXiv 2310.11511, Oct 2023; ICLR 2024): the LM is trained to emit reflection tokens. A `Retrieve` token (yes/no/continue) decides on demand whether to retrieve, and critique tokens (relevance, support, usefulness) score passages. At inference, a threshold on P(Retrieve=yes) tunes retrieval frequency against accuracy. In this approach the model decides, through training. [K] — [arXiv 2310.11511](https://arxiv.org/abs/2310.11511)
- **Adaptive-RAG** (Jeong et al., arXiv 2403.14403, Mar 2024; NAACL 2024): a small T5 classifier predicts query complexity and routes each query to no retrieval, single-step retrieval, or multi-step iterative retrieval. It is a pre-query gate that costs one small-model call. [K] — [arXiv 2403.14403](https://arxiv.org/abs/2403.14403)
- **DRAGIN** (Su et al., arXiv 2403.10081, Mar 2024; ACL 2024): RIND (real-time information-needs detection) combines token entropy, the attention influence of a token on later tokens, and a semantic/stopword filter to decide when to retrieve mid-generation. QFS builds the query from attention over the whole context rather than the last sentence. [K] — [arXiv 2403.10081](https://arxiv.org/abs/2403.10081)
- **SeaKR** (Yao et al., arXiv 2406.19215, Jun 2024): uses self-aware uncertainty from the LLM's internal hidden states to trigger retrieval and to rerank retrieved knowledge. As above, it is cheap but overconfident on multi-hop. [K] — [arXiv 2406.19215](https://arxiv.org/abs/2406.19215); evaluation in [arXiv 2501.12835](https://arxiv.org/html/2501.12835)
- **Popularity gating** (Mallen et al., "When Not to Trust Language Models", arXiv 2212.10511, Dec 2022; ACL 2023): on PopQA, retrieval helps mostly for long-tail (less popular) entities and can hurt for popular ones with large LMs. Retrieving only below a popularity threshold improved accuracy **and** reduced inference cost compared with always-retrieve. [K] — [arXiv 2212.10511](https://arxiv.org/abs/2212.10511)
- **ADAPT-LLM** (Labruna et al., "When to Retrieve", arXiv 2404.19705, Apr 2024): the LLM is fine-tuned to emit a special retrieve token when it does not know the answer, so retrieval happens only when necessary. It is reported to beat both always-retrieve and never-retrieve on PopQA. [K]/[S] — [arXiv 2404.19705](https://arxiv.org/pdf/2404.19705)
- **Generative Agents** (Park et al., arXiv 2304.03442, Apr 2023; UIST 2023): retrieval runs whenever the agent perceives, plans, reacts or converses. The score is a weighted sum of **recency** (exponential decay since last access), **importance** (an LLM-rated 1–10 poignancy score set at write time) and **relevance** (embedding similarity), each min-max normalized, with equal weights in the implementation. [K] — [arXiv 2304.03442](https://arxiv.org/abs/2304.03442)
- **MemoryBank** (Zhong et al., arXiv 2305.10250, May 2023; AAAI 2024): dense retrieval of past conversation memories to inform each response. Memory strength is updated with an Ebbinghaus-forgetting-curve rule, so memories that get recalled are reinforced and unused ones decay. [K] — [arXiv 2305.10250](https://arxiv.org/abs/2305.10250)
- **MemCon** ("Memory as a Controlled Process", Jiang et al., arXiv 2607.13591, v3 12 Oct 2026): memory access is an action space (Retrieve with tunable top-k and hop depth, PlanInject, Re-Retrieve with an "alternative approach" suffix when stuck, Consolidate, Forget, NoOp), chosen by a tabular **UCB bandit with no extra LLM calls**. With GPT-4.1-mini on ALFWorld: no memory 43.3%, G-Memory (static retrieval) 59.7%, MemCon 67.9%. Adding the learned controller to the static backend lifts ALFWorld from 59.7% to 64.9%, about 63% of the total gain. Input tokens are 10.9–24.1% lower than G-Memory. **Caveats:** there is no direct always-retrieve vs learned comparison and no retrieval-call counts. The claims that indiscriminate early retrieval dilutes the prompt and that stuck agents benefit from re-retrieval are motivation or design, not measured results. [V] — [arXiv 2607.13591](https://arxiv.org/html/2607.13591)
- Other 2025–2026 gating work found only via search, not verified: MemR³ (a router choosing retrieve/reflect/answer), Mem-π (arXiv 2605.21463; generates guidance only when it helps and abstains otherwise), and CAMeR (arXiv 2607.20458; keyword-gated hybrid activation). A Mem0 vendor page claims uncertainty-triggered retrieval cuts retrieval calls by 70–90%, which is unverified and should be treated with caution. [S] — [Mem-π](https://arxiv.org/pdf/2605.21463); [CAMeR](https://arxiv.org/pdf/2607.20458); [Mem0 library page](https://mem0.ai/library/agent-memory/reducing-hallucinations-llms-with-grounded-memory)

### Inferences
- Gating signals ranked by evidence: (1) **query or task type classifiers** (Adaptive-RAG style) are robust for multi-hop; (2) **token-level uncertainty** (FLARE, DRAGIN, entropy) is cheap and strong on single-hop but needs logit access, which hosted coding agents (Claude Code and similar) typically do not expose; (3) **internal-state probes** are cheap but overconfident; (4) **self-RAG-style trained tokens** need fine-tuning. For a coding agent on a closed API model, the practical signals are lexical or semantic novelty of the user prompt, task-start events, and explicit cues (file paths, error strings, "como fizemos", "decided"), not logits.
- The QA results transfer to agent memory only partly. QA retrieves from an encyclopedic corpus the model may already know. Project-specific memory (decisions, conventions) is almost by definition **not** in the model's parametric knowledge, which weakens the "model already knows it" argument against always-retrieving. The distractor argument (section 6) still applies.

### Gaps
- None of the verified sources ran a controlled always-retrieve vs gated retrieval comparison on **agent memory**. The QA studies are on Wikipedia QA, with mostly 8B-scale open models.
- "Proactive agents" work (e.g. ProactiveBench) addresses proactive task initiation rather than memory-retrieval timing. I did not verify it this session.

## 6. Evidence that irrelevant retrieved context hurts, and on deduplicating repeated context across turns

### Takeaway
Irrelevant context reliably hurts, and **semantically related but non-answering passages (what a top-k retriever returns when nothing truly relevant exists) are the most harmful kind**. Position also matters (lost in the middle), and returns diminish or reverse as the number of passages grows. I found **no academic study of cross-turn deduplication of injected memory**. That design choice rests on inference.

### Cited Findings
- **Distractibility:** Shi et al., "Large Language Models Can Be Easily Distracted by Irrelevant Context", arXiv 2302.00093 (Feb 2023; ICML 2023). Adding irrelevant sentences to math word problems (GSM-IC) sharply lowers accuracy. Mitigations include self-consistency and **instructing the model that it may ignore irrelevant information**. [K] — [arXiv 2302.00093](https://arxiv.org/abs/2302.00093)
- **Lost in the middle:** Liu et al., arXiv 2307.03172 (Jul 2023; TACL 2024). Multi-document QA accuracy follows a U-shape over the position of the relevant document. It is lowest in the middle and can fall below closed-book (no-document) performance. [K] — [arXiv 2307.03172](https://arxiv.org/abs/2307.03172); summarized in [search results](https://www.themoonlight.io/review/the-power-of-noise-redefining-retrieval-for-rag-systems)
- **Power of Noise:** Cuconasu et al., arXiv 2401.14887 (Jan 2024). The highest-scoring retrieved documents that do not contain the answer lower accuracy, and even one distracting document causes a noticeable drop. Random documents oddly raised accuracy by up to 35%, but only when few documents are retrieved. Their EMNLP 2025 follow-up: random passages do not affect answer quality, distracting passages do. [S]/[K] — [arXiv 2401.14887](https://arxiv.org/abs/2401.14887); [EMNLP 2025](https://aclanthology.org/anthology-files/pdf/emnlp/2025.emnlp-main.1422.pdf)
- **More passages first help, then hurt:** for many long-context LLMs, output quality first improves and then declines as the number of retrieved passages grows. Irrelevant passages from **strong** retrievers are more harmful than those from weak retrievers (Jin et al., arXiv 2410.05983). [S] — [arXiv 2410.05983](https://arxiv.org/html/2410.05983v1)
- **Robustness interventions:** Yoran et al., "Making Retrieval-Augmented Language Models Robust to Irrelevant Context", arXiv 2310.01558 (Oct 2023; ICLR 2024). Irrelevant retrieved context can make results worse than no retrieval. NLI-based filtering of passages, and fine-tuning on mixed relevant/irrelevant contexts, reduce the damage. [K] — [arXiv 2310.01558](https://arxiv.org/abs/2310.01558)
- **The same pattern in memory systems:** ReasoningBank's success rate drops monotonically from k=1 (49.7) to k=4 (44.4), attributed to "conflicts or noise" [V] — [arXiv 2509.25140](https://arxiv.org/html/2509.25140). A-MEM's accuracy plateaus or dips at high k [V] — [arXiv 2502.12110](https://arxiv.org/html/2502.12110).
- **Security dimension:** recent papers report that once memory retrieval is enabled, retrieved memory can dominate planning when it conflicts with the task, and that poisoning risk is highest with broad top-k semantic retrieval. This argues for small k and relevance thresholds. [S] — [arXiv 2603.15125](https://arxiv.org/html/2603.15125v1); [arXiv 2605.15338](https://arxiv.org/html/2605.15338v2)
- **Deduplication across turns:** none of the four systems' papers or the Hindsight integration guides I read describe suppressing memories that were already injected on earlier turns. [V] (absence in sources read) — [Hindsight guide](https://hindsight.vectorize.io/guides/2026/07/17/guide-claude-agent-sdk-memory-with-hindsight); [arXiv 2601.02163](https://arxiv.org/html/2601.02163)

### Inferences
- With always-retrieve, the failure mode to design against is "top-k always returns *something*". Without a **relevance floor (score threshold) and an empty result as a valid outcome**, every turn injects near-miss distractors, which is exactly the harmful category in Cuconasu et al. and Jin et al.
- Re-injecting the same memories on every turn of one session spends tokens. It also repeats content the model already has in context, which plausibly raises its salience in ways that can crowd out new instructions. Suppressing items already injected this session (by ID) is a low-risk optimization, but **it is not backed by a direct study**. If prompt caching is in use, repeated identical blocks at a stable prefix position are cheap, while blocks inserted per turn break the cache.

### Gaps
- No study measured cross-turn deduplication of memory injection. There is no direct measurement of how distraction from irrelevant memory (as opposed to Wikipedia passages) degrades coding-agent performance.

## 7. Tool-based (model decides) vs automatic per-turn memory retrieval in agents

### Takeaway
**I found no controlled, peer-reviewed study that varies only the retrieval trigger (tool vs automatic) in an agent loop.** What exists: production systems overwhelmingly ship automatic pre-turn or pre-task injection, often **combined** with model-callable tools (Hindsight hybrid; harness papers say most production systems use both). Vendor reports say model-driven, agentic querying wins on complex multi-hop questions at a latency and token cost. Benchmarks such as LongMemEval and LoCoMo retrieve once per question by construction, so they cannot settle the timing question.

### Cited Findings
- Hindsight's own docs present the choice as: tools when the agent should decide when memory matters, hooks when recall should happen every turn. Both can be combined over one bank. Hermes's default is "hybrid" (auto-inject before every turn plus tools). [V]/[S] — [Hindsight guide: Claude Agent SDK](https://hindsight.vectorize.io/guides/2026/07/17/guide-claude-agent-sdk-memory-with-hindsight); [Hermes provider blog](https://hindsight.vectorize.io/blog/2026/04/06/hermes-native-memory-provider)
- Vectorize's benchmark manifesto reportedly finds that "agentic" retrieval, where the LLM issues its own queries, is consistently better on complex and multi-hop questions, with a latency and cost trade-off. [S] (vendor, not opened) — [Hindsight blog](https://hindsight.vectorize.io/blog/2026/03/23/agent-memory-benchmark)
- The SemaClaw harness-engineering paper (arXiv 2604.11548) argues that loading memory **before execution** keeps constraints and prior decisions visible from the first reasoning step, and says most production systems combine a pre-retrieval pass with agent-initiated retrieval as the task unfolds. [S] (search summary only) — [arXiv 2604.11548](https://arxiv.org/pdf/2604.11548)
- A secondary roundup claimed that with a pre-seeded store, an agent made **0 memory tool calls in 114 turns**, while cue-based deterministic injection fired in every seeded run. **I could not trace this to a primary source**: the blog post I checked does not contain it. Treat it as unverified. [S] — [openchamber roundup](https://openchamber.dev/blog/agent-memory-research/); checked but absent in [sbatman post](https://sbatman.com/posts/2026-06-02-llm-memory-research-09/)
- **MemGPT** (Packer et al., arXiv 2310.08560, Oct 2023) is the canonical model-decides design: the LLM pages information in and out of context with function calls (searching recall and archival storage), prompted by system "memory pressure" events. It was not compared head-to-head against per-turn auto-retrieval under equal conditions. [K] — [arXiv 2310.08560](https://arxiv.org/abs/2310.08560)
- **LongMemEval** (Wu et al., arXiv 2410.10813, Oct 2024; ICLR 2025): 500 questions over long chat histories. Commercial chat assistants and long-context LLMs lose about 30% accuracy on memorizing information across sustained interactions. Retrieval improves with session decomposition (round-level values), fact-augmented key expansion, and **time-aware query expansion**. The setup is retrieve-per-question, so it cannot compare gating. [K] — [arXiv 2410.10813](https://arxiv.org/abs/2410.10813)
- **LoCoMo** (Maharana et al., arXiv 2402.17753, Feb 2024; ACL 2024): very long multi-session dialogues with QA, summarization and generation tasks. Its RAG baselines retrieve per question. [K] — [arXiv 2402.17753](https://arxiv.org/abs/2402.17753)
- Latency of automatic retrieval, from a memory system that reports it: Mem0 (Chhikara et al., arXiv 2504.19413, Apr 2025) reports **91% lower p95 latency and more than 90% token savings vs full-context** on LoCoMo, and a 26% relative judge-score gain over OpenAI memory. These are author-reported, and competitors (Zep, Letta) have publicly disputed the Mem0 LoCoMo comparisons. [K] — [arXiv 2504.19413](https://arxiv.org/abs/2504.19413)
- Retrieval-design cost note: one trajectory-memory paper points out that cosine-similarity retrieval needs no runtime LLM calls, while LLM-guided memory selection adds one call per task but handles nuance better. [S] — [arXiv 2603.10600](https://arxiv.org/pdf/2603.10600)

### Inferences
- Evidence-based policy for a coding agent, synthesized from the research rather than proven by any single study:
  1. **Automatic retrieval at task or session start and on each new user prompt.** Cheap hybrid retrieval with no LLM call, like A-MEM, ReasoningBank and Hindsight's per-turn hooks. Not on every tool step: no system above re-retrieves per tool call, and ReasoningBank retrieves once per task.
  2. **Small k (1–5) plus a relevance score floor, with an empty result allowed.** This follows ReasoningBank (k=1 best, k=4 worse), A-MEM's plateau, the distractor literature, and the security findings on broad top-k.
  3. **Inject distilled items** (decision, preference, pitfall) rather than raw transcripts, and tell the model explicitly to judge each item's relevance and ignore what does not apply. This combines ReasoningBank's per-step "discuss whether to use each memory" instruction with Shi et al.'s "ignore irrelevant info" mitigation.
  4. **Keep a model-callable recall tool** for deeper or multi-hop queries (the vendor-reported advantage of agentic retrieval), and do not rely on it alone. Models under-call memory tools, and that claim is anecdotal but consistent with the industry practice of shipping hybrid modes.
  5. **Gate cheaply where possible**: skip retrieval for trivial or continuation prompts ("ok", "continue"), and suppress items already injected this session. These follow from the efficiency findings of Moskvoretskii et al. and from the cost of repetition. Expensive gates (LLM sufficiency checks à la EverMemOS, Rowen-style consistency) are hard to justify per turn.
  6. **Time-aware query expansion and recency weighting** (LongMemEval; Generative Agents' recency × importance × relevance) are well supported as ranking features. They are not timing triggers.

### Gaps
- No controlled tool-vs-auto comparison on any coding benchmark (e.g. SWE-bench). No latency figures for Hindsight or EverMemOS recall. The "0 calls in 114 turns" anecdote is unverified. MemCon is the closest learned-timing study, but it reports no always-retrieve baseline or call counts.
- Several classic papers ([K]) were cited from their known arXiv records without re-fetching this session. Exact figures attributed to them should be confirmed before publication.
