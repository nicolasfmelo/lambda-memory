# How agent memory frameworks trigger and inject recall (Mem0/OpenMemory, Zep/Graphiti, Letta, LangMem/LangGraph, MemOS MemScheduler, Supermemory). State as of 2026-11-14

Method note: primary sources only where possible (official docs fetched 2026-11-14, papers, and shallow clones of the repos). Code was read at these commits: MemTensor/MemOS `3a16e5f` (2026-11-09), mem0ai/mem0 `main` (2026-11-06, sparse checkout of `integrations/claude-code-plugin`), supermemoryai/claude-supermemory `main` (2026-11-13). Each finding is labeled **[doc]** (official docs), **[code]** (repo source), **[paper]**, **[marketing/blog]** or **[3rd-party]**. Inferences are kept in their own subsections.

## Q1. When is retrieval triggered by default (every turn, every N turns, a tool call, a background process, or a scheduler)?

### Takeaway
No two vendors default to the same trigger. Zep, MemOS, the LangMem quickstart and Supermemory's Claude Code plugin retrieve deterministically before every turn, with the latest message(s) as the query. Mem0's own Claude Code plugin searches only on the first prompt of a session and leaves everything after that to a model-called tool. Letta keeps a pinned always-in-context tier, and the agent reads anything else on demand through file and tool calls. Only MemOS adds an LLM-gated "does working memory already answer this?" check plus a timer that forces a refresh.

### Cited Findings
**Mem0 (Platform/OSS v3; Claude Code plugin v0.3.1)**
- [code] The canonical `chat_with_memories` README example runs `memory.search(query=message, filters={"user_id": user_id}, top_k=3)` before every LLM call, puts the results in the system prompt under a "User Memories" heading, calls the LLM, and then calls `memory.add(messages, user_id=user_id)` after the reply. This is per-turn, pre-generation search. — [mem0 README](https://github.com/mem0ai/mem0)
- [doc] The search docs never say *when* to call search. They list use cases ("Context retrieval", "Personalization", "Fact checking" before responding) and require scoping: "Always provide at least a `user_id` filter". In v3 OSS, passing `user_id` as a top-level kwarg "raises `ValueError`". — [Mem0 search docs](https://docs.mem0.ai/core-concepts/memory-operations/search)
- [doc] Mem0's Claude Code plugin (v0.3.1) does automatic recall only "before Claude's first response in a new session". If that prompt is at least 20 characters, it "searches with that prompt and injects up to five relevant memories", and "No model is called to write the query." Later questions depend on Claude calling the single read-only `search_memories` tool, or on the user running `/mem0:search`. This tool replaced an earlier MCP server that had 9 read/write tools. — [Mem0 Claude Code docs](https://docs.mem0.ai/integrations/claude-code)
- [code] This is implemented in the `UserPromptSubmit` hook, `first_prompt_memory_output()`: "Search once before the agent handles the first prompt in a session". It returns `{}` when the prompt is not the first one. Settings: `MEM0_CODE_MIN_QUERY_CHARS` (default 20), query bounded to 6000 chars, `top_k=5`, `timeout=2` (s). The hook's own timeout in `hooks.json` is 6 s. — [hook_runner.py](https://github.com/mem0ai/mem0/blob/main/integrations/claude-code-plugin/core/hook_runner.py), [hooks.json](https://github.com/mem0ai/mem0/blob/main/integrations/claude-code-plugin/hooks/hooks.json)
- [doc] OpenMemory (Mem0's local MCP memory server) exposes the tools `add_memories`, `search_memory` and `list_memories`, so retrieval is model-invoked over MCP. — [Introducing OpenMemory MCP](https://mem0.ai/blog/introducing-openmemory-mcp), [docs.mem0.ai/openmemory](https://docs.mem0.ai/openmemory). The tool list comes from search-result summaries; I could not locate `openmemory/api/app/mcp_server.py` in the current `main` sparse checkout (it may have moved). There is also a hosted Mem0 MCP at `mcp.mem0.ai` — [Mem0 MCP docs](https://docs.mem0.ai/platform/mem0-mcp).

**Zep (v4 docs) / Graphiti**
- [doc] Default pattern: "Zep makes one retrieval call for each turn" with `client.thread.get_context(thread_uuid)`. The automatic search "uses the four most recent thread messages as its query and searches the full user graph." — [Zep: Retrieving context](https://help.getzep.com/v4/retrieving-context.md)
- [doc] Architecture Pattern 1 is deterministic: "Retrieve or assemble a context block from Zep on each turn", recommended when "one low-latency call on each turn gives the model enough context." Pattern 3 is tool-based: "The model decides whether and when to search", recommended for agents with "variable context needs". Pattern 4 makes two deterministic calls per turn, `thread.get_context()` for the user graph and `graph.get_context()` for the domain graph. — [Zep: Architecture patterns](https://help.getzep.com/v4/architecture-patterns.md)
- [doc] Graphiti's MCP server exposes `search_nodes`, `search_memory_facts`, `add_memory` and other tools. Retrieval is model-invoked, and the README calls the server "experimental" and a "reference implementation". — [Graphiti MCP README](https://github.com/getzep/graphiti/blob/main/mcp_server/README.md)
- [doc] The suggested Cursor rules use the prompt to force tool-based recall at task start: "**Always search first:** Use the `search_nodes` tool to look for relevant preferences and procedures before beginning work", and "**Search before suggesting:** Always check if there's established knowledge before making recommendations." — [Graphiti cursor_rules.md](https://raw.githubusercontent.com/getzep/graphiti/main/mcp_server/docs/cursor_rules.md)

**Letta (current: Letta Code / Agent SDK with MemFS; legacy: MemGPT-style blocks plus sleep-time agents)**
- [doc] Current MemFS: "Files at the memory root are loaded into the agent's system prompt on every turn." "Directories with their own `MEMORY.md` index stay out of context until they are needed." "Agents find memory in its Markdown files with normal file-search and read tools." There is no vector index by default. Keyword search comes from the MemFS Search mod, and semantic or hybrid search needs QMD. — [Letta MemFS](https://docs.letta.com/concepts/memfs/index.md)
- [doc] The Agent SDK page phrases the pinned tier differently: "Files under `system/` are in the system prompt every turn… Everything else stays out of context — the agent sees the file tree and reads what it needs." The MemFS page reconciles this: "Older agents use a `system/` directory for this instead." — [Letta SDK memory](https://docs.letta.com/agent-sdk/memory/index.md); contrast with [Letta MemFS](https://docs.letta.com/concepts/memfs/index.md)
- [doc] Recall outside the pinned tier is therefore agent-driven (file reads and searches). Conversation history search is separate: `letta messages search` offers full-text, vector and hybrid search on Cloud, and full-text only on local backends. — [Letta MemFS](https://docs.letta.com/concepts/memfs/index.md)
- [blog] Legacy sleep-time architecture (2025): the primary agent "can search its external memory" (conversation history and archival memory) through tools and has no core-memory editing tools. — [Letta blog, Apr 21 2025](https://www.letta.com/blog/sleep-time-compute)

**LangMem / LangGraph**
- [doc] The hot-path quickstart injects memory through a `prompt` function that runs before each model call: `memories = store.search(("memories",), query=state["messages"][-1].content)`. The results go into the system message inside `<memories>` tags. The agent also gets `create_manage_memory_tool`, and the docs mention `create_search_memory_tool` for "manually store and retrieve". — [LangMem hot path quickstart](https://langchain-ai.github.io/langmem/hot_path_quickstart/)
- [doc] Writes can happen on the "hot path" (agent tools, "adds perceptible latency") or in the "background" (an LLM reflects "after it ends or after a period of inactivity", with latency impact "None" and update speed "Delayed"). — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)

**MemOS (MemScheduler)**
- [code] `MOSCore.chat()` runs a synchronous `mem_cube.text_mem.search(query, top_k=self.config.top_k, …)` on every user query and builds the system prompt from the results. Before that, it submits a `QUERY` message to the scheduler, and after the reply it submits an `ANSWER` message. The scheduler handles both asynchronously. — [MemOS mem_os/core.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_os/core.py)
- [code] The scheduler only *refreshes working memory* when an LLM intent check says the current working memory is insufficient (`trigger_retrieval`), or when a timer fires (`query_trigger_interval`, default 10 s). Details are in Q5. — [memory_update_handler.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/task_schedule_modules/handlers/memory_update_handler.py), [general_monitor.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/monitors/general_monitor.py)

**Supermemory**
- [code] The Claude Code plugin's `UserPromptSubmit` hook (`recall-directive.js`) searches on every "substantive" prompt. The source comment explains: "Recall is performed HERE, not delegated to the model: the hook searches supermemory with the prompt itself and injects the top matches, so recall happens on every substantive prompt instead of only when the model chooses to spend a tool call. A configured recallDirective restores advisory mode." — [recall-directive.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/recall-directive.js)
- [doc] The plugin docs agree: "At session start, profile facts for this project are loaded into context." "Before Claude sees each substantive prompt, the hook searches Supermemory and injects fresh matches." "Set `recallDirective` to switch to advisory mode, where Claude decides when to search." For deeper history Claude can use the `context-gatherer` agent. — [Supermemory Claude Code docs](https://supermemory.ai/docs/integrations/claude-code.md)
- [doc] The AI SDK `withSupermemory` middleware is designed to "Automatically inject user profiles into every LLM call". It has three modes: `profile`, `query` (search on the user's message) and `full` (both). — [Supermemory docs page served at memory-router/overview.md](https://supermemory.ai/docs/memory-router/overview.md)
- [doc] The Memory Router / "Infinite Chat" is a transparent proxy that injects memory on every request (details in Q8). — [Supermemory search results: memory-router overview, Infinite Chat](https://supermemory.ai/docs/model-enhancement/context-extender.md)

### Inferences
- The industry default for chat products is deterministic pre-generation retrieval on every turn (Zep, the Mem0 README, the LangMem quickstart, MemOS, Supermemory's router, middleware and plugin). Tool-based retrieval is offered as the flexible or advanced option (Zep Pattern 3, OpenMemory and Graphiti MCP, Letta file reads).
- The two Claude Code plugins split cleanly. Supermemory runs `UserPromptSubmit` recall on every prompt, with filters and dedup. Mem0 runs it once, on the first prompt, then hands off to a tool. Both use `UserPromptSubmit` → `additionalContext` as the injection mechanism.

### Gaps
- I found no official Mem0 statement of *why* the plugin limits auto-recall to the first prompt (cost, noise, or latency). No changelog rationale was found.
- I could not confirm OpenMemory's current status (active vs folded into the hosted Mem0 MCP and plugin) in Nov 2026. Its source path was not found in `main`.

## Q2. Synchronous (blocking) vs asynchronous/prefetch, and published latency figures

### Takeaway
Every system runs the *read* synchronously on the turn's critical path. The async part is almost always the *write* or extraction, plus background curation (Letta dreaming and sleep-time, MemOS scheduler, LangMem background manager, Mem0 batch flush, Supermemory async Stop hook). Explicit prefetch exists in only two places: Zep's `graph.warm` and `return_context` on add, and MemOS's scheduler-curated working memory and KV cache. Latency numbers are mostly vendor-reported. The usable reference points are Mem0 search p50 0.148 s / p95 0.200 s (paper), Zep basic mode "P95 < 200ms" (blog, v3), and Supermemory profile "50-100ms" vs search "200-500ms" (docs table). Hook budgets in the real plugins are 2–4 s search timeouts.

### Cited Findings
- [paper] Mem0 (LoCoMo, Table 2): search p50 0.148 s and p95 0.200 s. Total (retrieval + answer) p50 0.708 s and p95 1.440 s, with 1,764 context tokens per query. Mem0g (graph): search p50 0.476 s / p95 0.657 s, total p95 2.590 s, 3,616 tokens. Full-context baseline: total p95 17.117 s at 26,031 tokens. The paper claims ~91–92% lower p95 than full-context. — [Mem0 paper arXiv 2504.19413](https://arxiv.org/html/2504.19413)
- [paper] Mem0 extraction runs on each new message pair. A separate "asynchronous module periodically refreshes the summary" so it "adds no processing delay". — [Mem0 paper](https://arxiv.org/html/2504.19413)
- [marketing/README] The Mem0 "New Memory Algorithm (April 2026)" benchmarks report end-to-end p50 of 0.88 s (LoCoMo, 7.0K tokens), 1.09 s (LongMemEval, 6.8K tokens) and ~1.0 s (BEAM), measured on the managed platform with "proprietary optimizations not available in the open-source SDK". — [mem0 README](https://github.com/mem0ai/mem0)
- [code] Mem0 plugin: the first-prompt search has `timeout=2` s inside a 6 s `UserPromptSubmit` hook. Capture is asynchronous: hooks save locally, and "A detached background worker sends a batch to Mem0 after every five completed exchanges". There is also an idle flush after 5 min (`MEM0_CODE_IDLE_FLUSH_SECONDS`), and session end or compaction flushes. — [hook_runner.py](https://github.com/mem0ai/mem0/blob/main/integrations/claude-code-plugin/core/hook_runner.py), [Mem0 Claude Code docs](https://docs.mem0.ai/integrations/claude-code)
- [marketing/blog] Zep v3 (Aug 7 2025): "For applications requiring reduced latency (P95 < 200ms), set `mode="basic"`". Summary mode, the default then, returns LLM-summarized context. — [Zep v3 blog](https://www.getzep.com/blog/zep-v3-context-engineering-takes-center-stage/). **Deprecated/changed:** the v4 docs no longer document `mode` or any P95 figure. The current v3 docs page also shows only `thread_id` plus an optional `template_id` — [Zep v3 retrieving-memory](https://help.getzep.com/v3/retrieving-memory).
- [doc] Zep v4 performance docs give no numbers: "Retrieval latency depends on the graph size, query, filters, result limits, deployment, and application network path… Measure end-to-end latency." Prefetch and overlap options: `return_context=True` on `thread.add_messages()` returns the Context Block in the same call, `graph.warm(user_uuid)` "before a likely retrieval, such as at login", and running add and search concurrently with `asyncio.gather`. — [Zep performance](https://help.getzep.com/v4/performance.md)
- [doc] Zep ingestion is asynchronous and slow: "Zep ingestion can take a few minutes", so the docs say to include the last 4–6 raw messages in the LLM call. — [Zep retrieving context](https://help.getzep.com/v4/retrieving-context.md)
- [paper] The Zep paper claims latency is reduced "by 90% compared to baseline implementations" (baselines not named in the abstract). — [Zep paper arXiv 2501.13956](https://arxiv.org/abs/2501.13956)
- [3rd-party benchmark run by a competitor] The MemOS paper (Table 7, LoCoMo over the network API, 10 QPS) reports search mean / P90 / P99 in ms: MemOS 440.5 / 528.4 / 777.1; Zep 571.7 / 614.8 / 5348.7; Mem0 1089 / 1397 / 4637; Supermemory 1057.1 / 1457.4 / 2107.6. At 40 QPS the success rates fall to 51.2% for Mem0 and 26.8% for Zep. Add mean: MemOS 191.9 ms, Zep 239.0 ms, Mem0 888.0 ms. — [MemOS paper arXiv 2507.03724v4](https://arxiv.org/html/2507.03724v4). Treat this as biased (vendor-run comparison).
- [paper] MemOS KV-cache ("activation memory") injection: TTFT reduction from 18.6% up to 94.2% (6,064-token context, 167-token query: 0.12 s vs 2.04 s). This holds only for local HuggingFace models. — [MemOS paper](https://arxiv.org/html/2507.03724v4)
- [code] The MemOS scheduler runs "without blocking main business logic". It uses a local queue or Redis Streams (`MOS_SCHEDULER_USE_REDIS_QUEUE`), a thread pool with default `thread_pool_max_workers=50`, and `consume_interval_seconds=0.01`. — [MemOS scheduler docs](https://memos-docs.openmem.net/open_source/modules/mem_scheduler/), [configs/mem_scheduler.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/configs/mem_scheduler.py), [general_schemas.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/schemas/general_schemas.py)
- [doc] Letta: dreaming "uses background subagents to review recent conversations… without interrupting your active work". Memory subagents "use git worktrees to update memory without blocking the main agent". — [Letta memory config](https://docs.letta.com/configuration/memory/index.md), [Letta MemFS](https://docs.letta.com/concepts/memfs/index.md)
- [doc] Supermemory profile vs search: profile response time "50-100ms" with "1 call", against search-based "200-500ms" with "3-5 queries". The measurement method is not stated. — [Supermemory user profiles](https://supermemory.ai/docs/concepts/user-profiles.md)
- [code] Supermemory plugin: `SEARCH_TIMEOUT_MS = 4000`, shrunk by time already spent fetching auth. The `UserPromptSubmit` hook timeout is 5 s and `SessionStart` is 30 s. The `Stop` capture hook is declared `"async": true` (timeout 30 s). — [recall-directive.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/recall-directive.js), [hooks.json](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/hooks.json)

### Inferences
- The "prefetch" in production plugins amounts to SessionStart profile loading plus a recent-query cache (Supermemory). Nobody computes next-turn recall in the background and injects it later in a Claude Code setting. MemOS's scheduler is the closest analogue: it curates working memory asynchronously after each query, and the next turn's synchronous search reads that curated working memory (see Q5).
- In practice the hook latency budget is "search must finish in about 2–4 s or be skipped". Both plugins fail open (Mem0 returns `{}`; Supermemory `continue: true` on auth or search failure).

### Gaps
- Zep v4 publishes no latency SLO. A "104/162 ms p50/p95 on LongMemEval" figure seen in search snippets could not be found on getzep.com/research, so I dropped it.
- I found no p50/p95 for Letta file or tool recall, LangMem `store.search`, or Supermemory's current v5 search API.

## Q3. Where retrieved memory is injected, and two-tier (always-on block plus on-demand search) patterns

### Takeaway
Every system now has a two-tier design. A small always-on tier holds a profile, core memory, pinned files or a user summary. A query-dependent tier is either searched per turn or reached through tools. Placement guidance differs. Mem0, the LangMem quickstart and MemOS use the system prompt. Zep v4 now explicitly says to keep memory **out** of system or privileged channels and to put it just before the latest user message, replacing the previous block. Claude Code plugins inject through `UserPromptSubmit`/`SessionStart` `additionalContext`.

### Cited Findings
- [code] Mem0 README: results go into the system prompt ("User Memories" bullet list). — [mem0 README](https://github.com/mem0ai/mem0)
- [code] Mem0 plugin: `hookSpecificOutput: {hookEventName: "UserPromptSubmit", additionalContext: context}`, headed "Mem0 found these relevant memories from earlier work in this repository:". Sidekick subagents receive the parent's already-recalled memories at `SubagentStart`. — [hook_runner.py](https://github.com/mem0ai/mem0/blob/main/integrations/claude-code-plugin/core/hook_runner.py), [Mem0 Claude Code docs](https://docs.mem0.ai/integrations/claude-code)
- [doc] Zep v4 placement: "Keep the Context Block out of system messages, developer messages, and other privileged instruction channels." For preloaded context, place it "after the conversation history and before the latest user request", framed as reference data, and "Replace the previous turn's block rather than appending a second one, which preserves the cacheable prefix." For tool-retrieved context it returns as a `tool_result`, or as a `Tool` message on OpenAI. — [Zep retrieving context](https://help.getzep.com/v4/retrieving-context.md), [Zep v3 retrieving-memory](https://help.getzep.com/v3/retrieving-memory)
- [doc] Zep Context Block contents: user summary (if enabled), facts with validity ranges such as `(2024-11-14 02:13:19+00:00 - present)`, entities, episodes, observations, thread summaries. "Smart Context Assembly" picks the types. Templates can override, for example `%{user_summary}`, `%{edges limit=10}`, `%{entities limit=5}`. — [Zep retrieving context](https://help.getzep.com/v4/retrieving-context.md)
- [doc] Letta's two tiers are root MemFS files in the system prompt every turn (or `system/` for older agents) plus everything else read on demand from the file tree. `/doctor` audits "system-prompt token usage". — [Letta MemFS](https://docs.letta.com/concepts/memfs/index.md), [Letta memory config](https://docs.letta.com/configuration/memory/index.md)
- [blog] Legacy Letta: in-context memory is "the memory stored in-context composed of memory blocks". External memory (conversation history and archival) is reached by search tools. — [Letta blog](https://www.letta.com/blog/sleep-time-compute)
- [doc] LangMem: memories go in the system message (`## Memories <memories>…</memories>`). Conceptually, a *profile* is "a single document updated in place", good for "quick access to current state". A *collection* is searched, useful "when you want to recall certain information contextually rather than every time". — [LangMem hot path](https://langchain-ai.github.io/langmem/hot_path_quickstart/), [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- [code] MemOS: `_build_system_prompt(memories_all, …)`, so memories go in the system message ahead of chat history. A custom `base_prompt` can contain a `{memories}` placeholder. Activation memory, when enabled on a HuggingFace backend, is passed as `past_key_values` (KV cache) rather than as text. — [MemOS core.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_os/core.py)
- [doc] Supermemory: a profile "rides along with every prompt", and the example puts static and dynamic facts in the system prompt. Profiles "complement" search, which returns "exact memories matching a query". A v5 profile call "takes no search query", so ranked memories need a separate `search()` with the same filter. — [Supermemory user profiles](https://supermemory.ai/docs/concepts/user-profiles.md)
- [code] Supermemory plugin tier 1: `SessionStart` injects profile `static` and `dynamic` facts, capped at `maxProfileItems` (default 5), as `additionalContext`. Tier 2: `UserPromptSubmit` injects fresh search hits as `additionalContext`. Tier 3: on-demand MCP `search_memory` (auto-approved by a `PreToolUse` hook) and the `context-gatherer` agent. — [session-start.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/session-start.js), [settings.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/lib/settings.js), [Supermemory Claude Code docs](https://supermemory.ai/docs/integrations/claude-code.md)

### Inferences
- Zep's v4 guidance against the system prompt (prompt-injection hygiene and cache-prefix preservation) suits Claude Code well. `UserPromptSubmit` `additionalContext` attaches to the current turn rather than the system prompt. That keeps the cacheable prefix stable and treats memory as data, not instructions.
- A plausible coding-agent mapping of the common two-tier design is: always-on = project profile and pinned decisions (SessionStart, or Letta root files / CLAUDE.md-style); per-prompt = top-k fresh hits (UserPromptSubmit); deep = MCP tool or subagent.

### Gaps
- No vendor documents how Claude Code positions `additionalContext` relative to cached prefixes. That belongs to the Claude Code hooks research track.

## Q4. Avoiding repeated memories every turn (dedup, novelty, working-memory cache) and token budgets

### Takeaway
Only Supermemory's Claude Code plugin and MemOS's scheduler implement explicit "don't re-inject what's already in context" logic. Supermemory keeps a per-session hash set of already-injected results and skips repeats. MemOS runs an LLM filter for "unrelated and redundant" items when replacing working memory. Zep instead *replaces* the block each turn. Mem0's plugin avoids the issue by recalling only once. Token budgets are mostly crude caps: top_k, character limits and profile item counts.

### Cited Findings
- [code] Supermemory plugin per-prompt recall pipeline: skip prompts under `MIN_PROMPT_LENGTH = 12` chars or starting with `/`, `!` or `#`. Query truncated to `MAX_QUERY_LENGTH = 500`. Filter `similarity >= MIN_SIMILARITY = 0.55`. Dedup within the batch by SHA-256 of normalized text, keep `MAX_RESULTS = 15`, truncate each to `MAX_RESULT_CHARS = 300`. Then drop any result whose hash is in the session's `recalled.json` ("seen" set, capped at `MAX_SEEN_HASHES = 500`) and inject only the `fresh` ones. If all are repeats, inject nothing. The status line reports "recalled N new · M already in context". — [recall-directive.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/recall-directive.js)
- [code] Supermemory also has `dedupeRecallQueries: true` by default, a recent-query result cache (`MAX_RECALL_CACHE = 50`) that serves repeated queries without an API call. — [settings.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/lib/settings.js), [lib/dedupe.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/lib/dedupe.js)
- [doc] Mem0 plugin caps: auto-recall up to 5 memories; explicit search `top_k` default 3 (range 1–20); `max_context_chars` default 4000 (range 1,000–10,000) per search output. The docs mention no relevance threshold and no dedup. — [Mem0 Claude Code docs](https://docs.mem0.ai/integrations/claude-code)
- [doc] Mem0 search knobs: `top_k`, `threshold`, `rerank` (default `False`). In v3, retrieval is "multi-signal" (semantic + BM25 + entity matching), and the April 2026 algorithm is "single-pass ADD-only extraction" with "no UPDATE/DELETE". This shifts dedup and conflict handling to retrieval and temporal reasoning. — [Mem0 search docs](https://docs.mem0.ai/core-concepts/memory-operations/search), [mem0 README](https://github.com/mem0ai/mem0)
- [doc] Zep: "Replace the previous turn's block rather than appending a second one". The Context Block "prefers recall over precision… the model ignores the irrelevant ones". Precision controls (limits, filters, reranker) require Advanced Context Block construction. Templates cap counts, for example `%{edges limit=10}`. — [Zep retrieving context](https://help.getzep.com/v4/retrieving-context.md)
- [code] MemOS `replace_working_memory`: LLM rerank of (current working memory + new candidates) against the query history, keeping `top_k`. Then `filter_unrelated_and_redundant_memories(...)` ("Apply combined filtering (unrelated + redundant)"). Working memory is capped by `working_mem_monitor_capacity` (default 30), and the activation monitor by 20. The scheduler `top_k` default is 5. — [base_mixins/memory_ops.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/base_mixins/memory_ops.py), [general_schemas.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/schemas/general_schemas.py)
- [code] MemOS intent gate: before retrieving, an LLM sees the query list plus the current working memory text and returns `trigger_retrieval` and `missing_evidences`. Retrieval runs only for the missing evidence, with `k_per_evidence = max(1, top_k // num_evidence)`. This is effectively a novelty and "already-have-it" check. — [memory_update_handler.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/task_schedule_modules/handlers/memory_update_handler.py), [mem_scheduler_prompts.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/templates/mem_scheduler_prompts.py)
- [doc] LangMem: recall "should combine similarity with 'importance' of the memory", together with "strength", which depends on recency and frequency of use. Over-extraction "lead[s] to reduced precision". The docs give no token-budget guidance. — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- [doc] Letta: `/doctor` audits "memory placement, duplication, and system-prompt token usage". The docs suggest moving bulky data to external storage and "keeping summaries and retrieval links in memory". Storage caps are 5 MiB (Free) and 50 MiB (Pro) per memory repo. — [Letta memory config](https://docs.letta.com/configuration/memory/index.md)
- [doc] Supermemory plugin always-on cap: `maxProfileItems` default 5 ("Max memories in context"). — [Supermemory Claude Code docs](https://supermemory.ai/docs/integrations/claude-code.md)

### Inferences
- In an append-only transcript like Claude Code, Zep's "replace the block" strategy isn't available, because `additionalContext` from earlier turns stays in history. Supermemory's per-session seen-hash set is the closest documented solution for hook-based injection.
- Compaction and clearing invalidate "already in context". Supermemory's code keys the seen set by `session_id` only. Whether it resets on `/compact` was not verified. Mem0's `SessionStart` matcher includes `startup|resume|clear|compact`, which suggests re-arming on those events.

### Gaps
- No vendor publishes an explicit per-turn token budget in tokens; all use counts or characters. Supermemory estimates cost at "~4 chars/token" only for display.
- I did not confirm whether Supermemory's `recalled.json` is cleared on compaction.

## Q5. MemOS MemScheduler: triggers, preload/activation, working vs long-term movement

### Takeaway
MemScheduler is an asynchronous, event-driven message-queue system. Every chat query emits a `QUERY` message, and every reply emits an `ANSWER` message. The handler extracts keywords, asks an LLM whether current working memory already covers the query, and only if it doesn't (or a 10 s timer has elapsed) retrieves for the "missing evidences". It then reranks, filters redundancy and replaces WorkingMemory, which the next turn's synchronous search reads first. Activation memory (KV cache) is an optional periodic refresh (default 300 s, disabled by default, HuggingFace backends only). The paper's "predictive preloading" framing is broader than what the code does.

### Cited Findings
- [doc] Task labels: `query`, `answer`, `mem_update`, `add`, `mem_read`, `mem_organize`, `pref_add`, `mem_feedback`, `api_mix_search`. `query` "Processes user queries, triggers intent recognition, memory retrieval, and converts them to memory update tasks". `mem_update` covers "extracting Query Keywords, updating Monitor, retrieving relevant memories, and replacing Working Memory." Memory moves between Working, Long-term and User layers, and logs record `from_memory_type`/`to_memory_type` (for example `LongTermMemory`→`WorkingMemory`). — [MemOS MemScheduler docs](https://memos-docs.openmem.net/open_source/modules/mem_scheduler/)
- [code] Trigger logic (`process_session_turn`): take current WorkingMemory (top_k) and call `monitor.detect_intent(q_list=queries, text_working_memory=…)`. If `trigger_retrieval` is false and `timed_trigger(last_query_consume_time, query_trigger_interval)` hasn't fired, it returns without retrieving ("Query schedule not triggered"). If the timer fired, retrieval is forced with the raw queries as the missing evidence. — [memory_update_handler.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/task_schedule_modules/handlers/memory_update_handler.py); `query_trigger_interval` default 10 — [general_monitor.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/monitors/general_monitor.py)
- [code] Intent prompt: "You are an advanced intent analysis system that evaluates answer satisfaction and identifies information gaps… We have enough information (satisfied) ONLY when: All question aspects are addressed; Supporting evidence exists in working memory…". Output is `{"trigger_retrieval", "evidences", "missing_evidences"}`. — [mem_scheduler_prompts.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/templates/mem_scheduler_prompts.py)
- [code] Working-memory replacement uses LLM rerank against the time-sorted query history (`process_and_rerank_memories`), keeps `top_k`, then runs `filter_unrelated_and_redundant_memories`, then updates the working-memory monitors (keyword-based scoring). — [memory_ops.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/base_mixins/memory_ops.py)
- [code] The next turn's synchronous search (`TreeTextMemory.search`, `memory_type="All"`) includes a "Retrieve and rerank from WorkingMemory" path in addition to LongTermMemory and UserMemory, so the scheduler's async curation feeds later turns. — [searcher.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/memories/textual/tree_text_memory/retrieve/searcher.py), [tree.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/memories/textual/tree.py)
- [code] Config defaults (`GeneralSchedulerConfig`): `top_k=5`, `context_window_size=5`, `act_mem_update_interval=300` s, `enable_activation_memory=False`, `working_mem_monitor_capacity=30`, `activation_mem_monitor_capacity=20`, `enable_parallel_dispatch=True`, `thread_pool_max_workers=50`. — [configs/mem_scheduler.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/configs/mem_scheduler.py), [general_schemas.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/schemas/general_schemas.py)
- [code] Activation memory: after a working-memory update, if enabled, `update_activation_memory_periodically` runs. Activation-monitor items are ranked by `importance_score`. At chat time the KV cache is passed as `past_key_values`, and only for HuggingFace backends ("Activation memory only used for huggingface backend. Skipping…"). — [memory_update_handler.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/task_schedule_modules/handlers/memory_update_handler.py), [general_monitor.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_scheduler/monitors/general_monitor.py), [core.py](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_os/core.py)
- [paper] Paper framing: MemScheduler selects memory types "based on task intent and context" and "optimizes memory selection using metrics like contextual similarity, access frequency, temporal decay, and priority tags". "Stable, frequently accessed content is transformed into Activation Memory for KV caching, minimizing prefill latency." Frequently recalled plaintext "may be promoted" to KV; stable templates are distilled into parameters; underused KV is downgraded to plaintext or cold storage. MemLifecycle states are Generated → Activated → Merged → Archived (→ Expired/Frozen). The pipeline order is parsing → scheduling → injection → generation. No numeric promotion thresholds are given. — [MemOS paper v4](https://arxiv.org/html/2507.03724v4)
- [marketing/doc] Docs summary (via search snippet): scheduling "predicts which memories will be needed and preloads high-efficiency types like activated and working memories" (Parameter > Activated > Working > Other Plaintext). — [MemOS memory scheduling (search result)](https://memos-docs.openmem.net/overview/quick_start/mem_schedule). That page now returns 404, and I found no prediction model beyond the intent gate in the code.

### Inferences
- In code, the "prediction" is reactive and one turn behind. The scheduler uses the current query (and answer) to pre-stage WorkingMemory for the *next* query. This is a sound pattern for a Claude Code hook: do an async curation step after each prompt (or on Stop), then a cheap read of the curated set on the next `UserPromptSubmit`.
- The LLM intent gate ("is working memory sufficient?") is an explicit novelty check that avoids redundant retrieval. It costs an extra LLM call per query, which is acceptable only because it runs off the critical path.

### Gaps
- No scheduler ablation or latency benefit is isolated in the paper ("not isolated experimentally").
- The prompt for `filter_unrelated_and_redundant_memories` and the keyword scoring weights were not read.

## Q6. Letta sleep-time compute: what runs between turns and how it changes context

### Takeaway
Letta has two generations. The 2025 "sleep-time agent" was a second agent sharing memory blocks with the primary. It owned all core-memory editing tools and ran asynchronously every N steps (default 5), rewriting the blocks that are recompiled into the primary's context. The current Letta Code / Agent SDK (MemFS) replaces this with "dreaming": background subagents, triggered every N steps or on compaction, that commit consolidated lessons to the git-backed memory repo in a worktree. Root files, which are always in the system prompt, then change on later turns. Either way, background compute changes the *always-on tier* rather than injecting search results.

### Cited Findings
- [doc/search-snippet] Legacy: `enable_sleeptime: true` at agent creation (or via update) creates a background agent that "can modify the memory blocks asynchronously". It runs on a schedule that "defaults to every 5 steps", configurable through `sleeptime_agent_frequency`. — [Letta sleep-time guide (search index)](https://docs.letta.com/guides/agents/architectures/sleeptime/index.md). The page returned 404 on 2026-11-14, which is likely a legacy doc removed in the docs restructure.
- [blog] The primary agent cannot edit core memory. The sleep-time agent "has the ability to manage _both_ the in-context memory of the primary agent as well as its own". Memory management happens "asynchronously" and in an "'anytime' fashion", so the primary reads the current state without waiting. "The higher the frequency setting, the more tokens your agent will use." The motivation: doing memory operations during conversation makes the agent "slower". — [Letta blog, Apr 21 2025](https://www.letta.com/blog/sleep-time-compute)
- [paper] Sleep-time compute (Lin, Snell, Wang, Packer, Wooders, Stoica, Gonzalez; arXiv 2504.13171, Apr 17 2025) precomputes inferences about the context offline. Results: "~5x" less test-time compute at equal accuracy (Stateful GSM-Symbolic / AIME), accuracy up "13%" and "18%", and 2.5x lower average cost per query when several queries share a context. Effectiveness correlates with query predictability. — [arXiv 2504.13171](https://arxiv.org/abs/2504.13171)
- [doc] Current dreaming: `createAgent({ dreaming: { trigger: "off" | "step-count" | "compaction-event", behavior: "reminder" | "auto-launch", stepCount } })`. `behavior` "can only be set at agent creation". Sessions can override `trigger` and `stepCount`. The example uses `stepCount: 25`, and the docs state no default. — [Letta SDK memory](https://docs.letta.com/agent-sdk/memory/index.md)
- [doc] Dreaming "uses background subagents to review recent conversations, consolidate useful lessons, and update memory without interrupting your active work". It runs "after a set number of completed agent steps or when the context window is compacted" (`/sleeptime` in the CLI). An optional "Agent reviews before applying" setting adds a second background review pass with more tokens and no user approval. — [Letta memory config](https://docs.letta.com/configuration/memory/index.md)
- [doc] Every memory edit is a git commit. Background memory subagents (dreaming, memory doctor) use git worktrees. Root files load into the system prompt "on every turn", so committed changes reach context on subsequent turns. — [Letta MemFS](https://docs.letta.com/concepts/memfs/index.md)

### Inferences
- Letta's model maps naturally to Claude Code. A background consolidation job (Stop / PreCompact hook, or every N turns) rewrites a small pinned file that CLAUDE.md or SessionStart already loads, while per-prompt retrieval stays optional. The "compaction-event" trigger is notable, because PreCompact is a natural hook point for consolidation.

### Gaps
- The current docs give no default for dreaming `trigger` or `stepCount`. The legacy "every 5 steps" default could not be re-fetched from the live page.
- I did not verify whether legacy `enable_sleeptime` is still accepted by the current Letta server API, or formally deprecated.

## Q7. Zep context block / memory.get pattern and Graphiti search usage in agents

### Takeaway
Zep's recommended loop is per turn: add messages, then get the context block, ideally in one call with `return_context=True`. Inject the block as data just before the latest user message, replacing the previous one, and also send the last 4–6 raw messages because ingestion lags by minutes. The API lineage is v2 `memory.get` → v3 `thread.get_user_context(mode="summary"|"basic")` → v4 `thread.get_context(thread_uuid, template_uuid?)`. The "basic mode P95 < 200 ms" claim is v3-era and absent from v4 docs. Graphiti exposes search as MCP tools and relies on rules prompts that tell the agent to "always search first".

### Cited Findings
- [blog] v3 (Aug 7 2025) renamed `session`→`thread` and `group`→`graph`. `get_user_context` returned summarized context by default, while `mode="basic"` returned raw facts and entities "matching the v2 `memory.get` call", with P95 < 200 ms. The blog notes that v4 is now available. — [Zep v3 blog](https://www.getzep.com/blog/zep-v3-context-engineering-takes-center-stage/)
- [doc] v4 offers three ways to build the block: the default Context Block (fixed format), custom templates (`template_uuid`, "Create the template once, store its UUID"), and Advanced Context Block construction from graph search (`graph.query` "experimental and in closed release"). — [Zep retrieving context](https://help.getzep.com/v4/retrieving-context.md)
- [doc] The automatic query is the "four most recent thread messages". For complex tasks the docs suggest "an agent that plans several targeted retrieval calls through tools". — [Zep retrieving context](https://help.getzep.com/v4/retrieving-context.md)
- [doc] Search-query guidance: keep queries "concise and specific", because "Longer queries may not improve search quality and will increase latency." — [Zep performance](https://help.getzep.com/v4/performance.md)
- [doc] Graphiti MCP: `search_nodes` (entity_types, center_node_uuid) and `search_memory_facts` (edge_types, valid_at/invalid_at). Ingestion is async and queue-based, with `SEMAPHORE_LIMIT` default 10, and "each episode involves multiple LLM calls". — [Graphiti MCP README](https://github.com/getzep/graphiti/blob/main/mcp_server/README.md)
- [doc] The Graphiti rules for coding agents say: "Always search first… before beginning work", "Filter by entity type: Specify `Preference`, `Procedure`, or `Requirement`", and "Capture requirements and preferences immediately… use `add_memory`". — [cursor_rules.md](https://raw.githubusercontent.com/getzep/graphiti/main/mcp_server/docs/cursor_rules.md)

### Inferences
- Zep's own Claude-facing guidance (return the block as `tool_result` when it may contain third-party data) suggests that, with Anthropic models, Zep sees hook-style injection as less safe than tool results. This matters for untrusted memory content in `additionalContext`.

### Gaps

## Q9. Explicit guidance or benchmarks comparing per-turn retrieval vs tool-based retrieval

### Takeaway
I found no controlled benchmark from any vendor that compares per-turn injection with model-invoked tool retrieval on the same task. The guidance is qualitative and split. Zep frames it as determinism vs flexibility. Supermemory's plugin code explicitly chose per-prompt hooks because models don't reliably spend tool calls. Mem0's plugin chose first-prompt-only plus a tool. Graphiti and Letta rely on prompting the agent to search. Published benchmarks (Mem0, Zep, MemOS) all measure per-query retrieval pipelines, not agentic tool use.

### Cited Findings
- [doc] Zep: deterministic per-turn retrieval "happens on every turn, whether or not the model needs it". The tool-based approach is "more flexible but less deterministic", and "One search tool without domain knowledge might return related facts of low value", so tools should be paired with domain knowledge and a planning step. — [Zep architecture patterns](https://help.getzep.com/v4/architecture-patterns.md)
- [doc] Zep: the default block is biased to recall, with the model ignoring irrelevant facts. Complex tasks benefit from multi-call tool retrieval. — [Zep retrieving context](https://help.getzep.com/v4/retrieving-context.md)
- [code] Supermemory chose the hook so that recall "happens on every substantive prompt instead of only when the model chooses to spend a tool call". Advisory, model-decides mode is opt-in through `recallDirective`. — [recall-directive.js](https://github.com/supermemoryai/claude-supermemory/blob/main/plugin/hooks/recall-directive.js)
- [doc] Mem0 plugin: one automatic recall, then "Claude can call the `search_memories` tool with a specific question". The plugin consolidated to a single read-only tool, replacing a 9-tool MCP server. — [Mem0 Claude Code docs](https://docs.mem0.ai/integrations/claude-code)
- [doc] LangMem: hot-path memory tools add "perceptible latency to user interactions", while background processing has "None". This applies to writes. For reads, the quickstart uses deterministic `store.search` in the prompt function together with optional search tools. — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/), [LangMem hot path](https://langchain-ai.github.io/langmem/hot_path_quickstart/)
- [blog] Letta moved memory *editing* off the conversational path because doing it in-turn makes the agent "slower". Reads remain always-in-context plus tool or file search. — [Letta blog](https://www.letta.com/blog/sleep-time-compute)
- [paper] Mem0, Zep and MemOS evaluations (LoCoMo, LongMemEval, DMR) retrieve per question and inject the result. None tests an agent deciding when to call memory. — [Mem0 paper](https://arxiv.org/html/2504.19413), [Zep paper](https://arxiv.org/abs/2501.13956), [MemOS paper](https://arxiv.org/html/2507.03724v4)

### Inferences
- The convergent hybrid across vendors is: (1) a small always-on tier (profile, pinned files, user summary); (2) cheap deterministic per-prompt recall gated by prompt length and type, a similarity threshold and session dedup, with a hard 2–4 s timeout and fail-open behavior; (3) a model-invoked tool or subagent for deep or multi-hop recall; and (4) asynchronous write and consolidation (Stop / every N exchanges / idle / compaction). MemOS adds an optional fifth part, an async "is current working memory sufficient?" gate that pre-stages the next turn.
- The Mem0 vs Supermemory split is a live design question for coding agents. Per-prompt injection risks noise and token creep in long sessions, which is why Supermemory added seen-hash dedup and a 0.55 similarity floor. First-prompt-only risks missed recall on topic shifts mid-session.

### Gaps
- I found no published A/B or benchmark of per-turn vs tool-based recall, by vendors or academics, within this scope. Any claim about which is "better" for coding agents would be inference.
- I didn't fetch LangMem's background `ReflectionExecutor` and debounce docs or the LangGraph long-term memory docs, so the exact delay defaults are unverified.
